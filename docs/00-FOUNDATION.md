## 1. 제품 정의

### 한 문장
> **core_task는 4~20명 웹 개발회사에서, PM이 매주 업무를 배정하고 팀원이 자기 업무만 보며 일하는 흐름을 도구 하나로 끝내는 업무관리 시스템이다.**

### 우리가 푸는 진짜 문제
Notion이 느리거나 Jira가 못생겨서 만드는 게 아니다. 실제 문제는 이거다.

| 현재 겪는 일 | 원인 |
|---|---|
| 업무 배정이 카톡·구두·회의로 흩어진다 | 배정 행위 자체가 도구에 없음 |
| PM이 "지금 누가 뭘 하고 있지?"를 물어봐야 안다 | 담당자 축으로 전체를 보는 화면이 없음 |
| 팀원은 도구를 열면 남의 업무까지 보여 피로하다 | 개인 뷰가 부가기능임 |
| 도구를 도입해도 2주 뒤 아무도 안 쓴다 | 입력 비용 > 얻는 이득 |

**따라서 core_task의 승부처는 기능 수가 아니라 "입력 비용을 얼마나 낮추느냐"다.**
이 문장이 이후 모든 설계 판단의 기준이다.

### 대상
- **회사 규모**: 4~20명 웹 개발회사
- **1차 사용자**: PM (배정하는 사람) — 이 사람이 안 쓰면 제품 자체가 죽는다
- **2차 사용자**: Frontend / Backend / Designer / Marketer (수행하는 사람)
- **비대상**: 프리랜서 개인, 50명 이상 조직, 외부 클라이언트 협업

### 성공 기준 (원문에 없던 항목 — 이게 없으면 기능 판단이 불가능하다)

| 구분 | 지표 | 목표 |
|---|---|---|
| 활성화 | 팀원이 가입 첫 주에 **본인 Task 상태를 직접 1회 이상 변경** | 80% |
| 핵심 습관 | **PM이 주 1회 이상 배정 보드에서 드래그로 배정** | 매주 |
| 지속 | 도입 4주차 **주간 활성 팀원 비율** | ≥ 80% |
| 대체 | 업무 배정이 카톡/엑셀로 나가는 비율 | 0에 수렴 |

**중단 기준 (Kill Criteria)**
도입 4주가 지나도 팀이 여전히 카톡으로 업무를 나눈다면, 기능을 추가하지 말고 **왜 안 쓰는지부터 다시 조사한다.** 기능 추가는 이 상황의 해법이 아니다.

## 2. 설계 원칙

### 제품 철학
1. **Task가 실행의 최소 단위, Project는 관리의 단위다.** 두 역할을 섞지 않는다.
2. **리드는 전체를 보고, 팀원은 자기 것만 본다.** 단, "전체"의 범위는 사람마다 다르다 — **내가 Lead인 프로젝트만이 내 전체다** (§3 참조). 그리고 리드도 자기 업무를 수행하므로 개인 화면을 똑같이 갖는다.
3. **배정은 드래그 한 번으로 끝난다.** 배정이 폼 입력이 되는 순간 이 제품은 실패한다.
4. **팀원도 자기 업무를 스스로 만들 수 있다.** 아래에서 위로 올라오는 일이 실제 업무의 절반이다.
5. **Notion보다 단순하고, Jira보다 배우기 쉽다.** 설명서 없이 5분 안에 쓸 수 있어야 한다.

### 새 기능을 넣기 전 통과해야 할 4가지 질문
1. 이 기능이 없으면 **무엇이 카톡으로 새어나가는가?**
2. **PM이 쓰는가? 팀원이 쓰는가?** (둘 다 아니면 만들지 않는다)
3. **입력 비용이 얻는 이득보다 작은가?** (아무도 안 채울 필드는 없는 필드다)
4. **주 1회 이상 쓰이는가?** (아니면 최상위 메뉴가 될 수 없다)

### UX 원칙
- 불필요한 클릭을 최소화한다. **자주 하는 일일수록 화면 깊이가 얕아야 한다.**
- 빈 화면을 방치하지 않는다. 첫날 텅 빈 대시보드는 이탈의 1순위 원인이다.
- 파괴적 동작(삭제·완료 확정)만 확인을 받는다. 나머지는 즉시 실행하고 되돌리기(Undo)를 준다.
- 팀원 시나리오는 **모바일에서 동작해야 한다.** 출근길에 "오늘 뭐 하지"를 폰으로 본다.

## 3. 사용자와 역할

### 원문 비판 — 전역 role(PM / Member)은 소규모 팀에서 깨진다

원문은 사용자를 계정 단위로 `PM` 또는 `Member`로 나눴다. 4~20명 회사에서 이건 현실과 안 맞는다.

- PM도 실무를 한다 → PM에게 "내 업무" 화면이 없다는 뜻이 된다
- 원문 내부 모순: `vision`에는 "팀원도 자신의 업무를 추가할 수 있다"인데, `roles.Member.permissions`에는 업무 생성 권한이 없다

### 재정립 ① — 모두가 Member다. 관리자는 권한이 더 있는 Member다 ✅

> **`PM`은 별도의 사용자 종류가 아니다. 추가 권한을 가진 Member다.**
> 따라서 관리자에게도 "내 업무" 화면·개인 보드·개인 대시보드가 **전원과 동일하게** 제공된다.

### 재정립 ② — 역할은 2단이다. 프로젝트마다 리드가 다르기 때문이다 ✅

이 회사에서는 **프로젝트마다 리드가 다르다** (A 프로젝트는 대표, B 프로젝트는 시니어 개발자).
전역 역할 하나로는 표현할 수 없다. 그래서 역할을 **워크스페이스 단위**와 **프로젝트 단위**로 나눈다.

**① 워크스페이스 역할** — "이 회사에서 무엇을 할 수 있는가"

| 역할 | 설명 |
|---|---|
| `Member` | **전원의 기본값.** 소속 프로젝트에서 일한다 |
| `Admin` | Member + 멤버 초대/제거, 프로젝트 생성, **전 프로젝트 접근** |
| `Owner` | Admin + 워크스페이스 설정·결제·양도 |

**② 프로젝트 역할** — "이 프로젝트에서 무엇을 할 수 있는가"

| 역할 | 설명 |
|---|---|
| `Member` | 업무 생성, 본인 업무 상태 변경(**`in_review`까지**), 댓글, 프로젝트 조회 |
| `Lead` | Member + **업무 배정**, **완료 확정**, 프로젝트 설정·멤버 관리 |

**`Viewer`는 만들지 않는다.** 4~20명 회사에서 "보기만 가능한 사람"은 실존하지 않는다. 아무도 안 쓰는 권한 티어는 코드와 UI만 복잡하게 만든다.

### 이 2단 구조가 만드는 규칙

| 행동 | 필요 권한 |
|---|---|
| 회사 멤버 초대 · 프로젝트 생성 | 워크스페이스 `Admin` |
| 프로젝트 설정 · 프로젝트 멤버 추가 | 그 프로젝트의 `Lead` |
| **업무 배정** (남에게) | 그 프로젝트의 `Lead` |
| **완료 확정** (`in_review → done`) | 그 프로젝트의 `Lead` |
| 업무 생성 · 본인 상태 변경 · 댓글 | 그 프로젝트의 `Member` |

**핵심 규칙: 프로젝트 `Member`는 Task를 `done`으로 옮길 수 없다. `in_review`까지만 올린다. `done` 확정은 그 프로젝트 `Lead`의 권한이다.**
→ 원문의 "업무 완료 요청"이라는 표현을 이렇게 명문화한다. 이건 좋은 결정이었고 유지한다.

**부가 규칙 (데드락 방지)**
- **워크스페이스 `Admin`은 모든 프로젝트에서 `Lead` 권한을 갖는다.** 리드가 휴가면 아무도 완료 확정을 못 하는 상황을 막는다. 단, 이런 개입은 활동 로그에 남는다.
- **프로젝트 Lead는 여러 명일 수 있다.** 부재 대비.
- **프로젝트 생성자는 자동으로 그 프로젝트의 Lead가 된다.**

### 이 구조의 자연스러운 귀결 — 사람마다 "전체"의 범위가 다르다

시니어 개발자가 B 프로젝트의 Lead라면, 그 사람의 화면은 이렇게 된다.

```
B 프로젝트  →  전체 보기 (배정 보드 · 팀원 업무량 · 리뷰 대기)   ← Lead니까
그 외 프로젝트 →  내 업무만                                    ← Member니까
```

**대시보드 "전체 보기"의 범위 = 내가 Lead인 프로젝트들.** (워크스페이스 Admin은 전 프로젝트)
역할을 사람에 붙이지 않고 프로젝트에 붙였기 때문에 이게 자동으로 성립한다.

### 화면은 역할이 아니라 "뷰"로 나눈다

원문의 *"PM과 팀원의 화면은 완전히 다르게 구성한다"* 는 **절반만 맞는 원칙이라 다듬는다.**

> **수정된 원칙: 보드는 목적이 달라 화면이 다르다. 그러나 데이터는 하나다.**
> - **배정 보드**(사람 축)와 **내 업무 보드**(상태 축)는 실제로 다른 화면이다. → 원문 의도 존중 ✅
> - 다만 두 보드는 **같은 `Task.status`, 같은 `Task.assigneeId`를 공유**한다. 상태를 두 벌로 관리하지 않는다. (근거는 §6.1)
> - **Lead도 Member이므로 두 보드 모두에 접근한다.** 기본 진입점만 다르다 (Lead → 배정 보드, Member → 내 업무 보드).

## 4. 핵심 개념 모델

```
Workspace (회사)
 └ Project (관리 단위)
     ├ Task (실행 단위)  ← 제품의 심장
     ├ Meeting (회의록)
     ├ Document (문서)
     └ Member (프로젝트 참여자 + 역할)
```

- **Task는 반드시 Project에 속한다.** 프로젝트 없는 업무는 만들지 않는다 (분류 불가 데이터가 쌓이면 대시보드가 거짓말을 시작한다). 대신 워크스페이스마다 **`개인 업무`** 프로젝트를 자동 생성해 도피처를 준다. (`기타`가 아니다 — "기타"는 쓰레기통이 되고, "개인 업무"는 용도가 명확해 오히려 정상 프로젝트 생성을 유도한다)
- **Task는 담당자가 없을 수 있다** (`assigneeId = null` → 배정 대기 상태).
- **Meeting의 Action Item은 Task를 만든다.** 회의록에 적힌 할 일이 Task가 되지 않으면 회의록 기능은 죽은 기능이다. 이 연결이 Meeting 기능의 존재 이유다.

### 프로젝트 내부 탭

**원문 (장기 목표)**
```
개요 · 일정 · Tasks · Meetings · Documents · 팀원 · 설정
```

**v1 확정 — 4개** (상세는 [02-IA.md](02-IA.md) §4)
```

```

### 구조 축 — C안 확정 ✅

```
Dashboard  →  Project  →  Task
 전체 조망     관리 단위    실행 단위
```

원문의 C안 선택에 동의한다. 근거도 정확하다: **PM은 프로젝트 단위로 사고하고, 실무자는 Task 단위로 일한다.** 두 사고방식이 각자의 진입점을 갖는 유일한 구조다.

## 6. 핵심 화면과 동작

### 6.1 보드 설계 — 사람 중심 칸반을 유지하되, 축을 분리한다

원문 설계:
```
Backlog → FE1 → FE2 → Designer → Backend → Review → Done
         └────── 사람 ──────┘   └── 상태 ──┘
```

**원문의 방향(사람을 컬럼으로)은 채택한다.** 프로젝트 스코프에서 컬럼은 그 프로젝트 멤버 수(3~6명)이므로 폭주하지 않는다.
다만 위 배열에는 **한 줄에 사람 축과 상태 축이 섞여 있는** 결함이 있다.

**깨지는 지점:** 김프론트가 맡은 업무가 리뷰 단계에 들어갔다. 어느 컬럼에 있어야 하는가?
- `Review` 컬럼에 두면 → **담당자 정보가 보드에서 사라진다.** "김프론트가 지금 몇 개 물고 있나"를 볼 수 없다. 사람 컬럼을 만든 이유가 무너진다.
- `김프론트` 컬럼에 두면 → **`Review` 컬럼은 영원히 비어 있다.** 대시보드 "리뷰 대기" 위젯이 근거를 잃는다.

둘 다 성립하지 않는다. 하나의 컬럼 행에 두 축은 들어갈 수 없다.

### 확정 설계: 컬럼은 사람, 상태는 카드 ✅

**상태 (단일 진실 — 두 보드가 공유한다)**
```
todo → in_progress → in_review → done
예정      진행중        리뷰중       완료
```

**`backlog` 상태는 두지 않는다 (D-018).** "미배정"은 상태가 아니라 `assigneeId IS NULL` 이다.
같은 사실을 `status` 와 `assigneeId` 두 곳에 저장하면 반드시 어긋나기 때문이다 — 배정은 됐는데 status가 `backlog`로 남은 카드는 배정 보드에선 담당자 컬럼에, 대시보드에선 미배정으로 집계된다.

| 개념 | 판정 기준 |
|---|---|
| 미배정 | `assigneeId IS NULL` |
| 배정한다 | `assigneeId` 를 설정한다. `status` 는 건드리지 않는다 |
| 담당자를 뗀다 | `assigneeId = NULL`. 자동으로 미배정 컬럼으로 돌아간다 |

덕분에 상태 4개가 내 업무 보드의 컬럼(예정/진행중/리뷰/완료)과 **정확히 1:1로 대응**한다.

**① 배정 보드 (그 프로젝트 Lead의 기본 화면 / 프로젝트 내부 전용)**

컬럼 = `미배정` + **해당 프로젝트 멤버**. `Review`와 `Done`은 컬럼이 아니라 **카드 뱃지**로 내린다.

```
 미배정          김프론트            이백엔드          박디자인
┌──────────┐   ┌──────────────┐   ┌────────────┐   ┌────────────┐
│ 결제 연동  │   │ 로그인 API    │   │ 스키마 설계  │   │ 상세 페이지  │
│           │   │ 🟡진행중 · 3일 │   │ 🔵예정      │   │ 🟣리뷰      │
├──────────┤   ├──────────────┤   └────────────┘   └────────────┘
│ 배너 교체  │   │ 소셜 로그인    │
│           │   │ 🟣리뷰        │
└──────────┘   └──────────────┘

[전체] [진행중] [리뷰 대기] [지연]   ← 필터 칩
```

- **드래그 = 담당자 변경, 그것뿐.** 미배정 카드를 사람에게 떨구면 `assigneeId` 만 설정된다. 상태 자동 전이 같은 특수 규칙이 없다.
- **단, 마감일이 비어 있으면 드롭 직후 마감일 퀵칩 팝오버가 뜬다** (D-021b). 이미 있으면 뜨지 않는다 — 배정은 여전히 드래그 한 번이다.
- **카드 상태 뱃지**로 "누가 / 어느 단계"를 동시에 해결한다.
- **필터 칩**으로 "리뷰 대기만", "지연만"을 **화면 이동 없이** 그 자리에서 본다. Lead가 가장 자주 던지는 질문이라 최상단에 고정한다.
- **드래그 배정은 Lead에게만 활성화**된다. 일반 Member에게는 읽기 전용 보드로 보인다.
- `done` 카드는 컬럼을 어지럽히므로 기본 숨김(완료 N일 경과 시 접힘).

**② 내 업무 보드 (Member 기본)**

컬럼 = 상태. 본인 담당 업무만 필터.
```
예정 → 진행중 → 리뷰 → 완료
```
- **드래그 = 상태 변경.**
- 프로젝트 Member는 `완료` 컬럼에 드롭할 수 없다. `리뷰`까지만 (§3 규칙).
- **Lead도 이 보드를 쓴다.** 자기 업무를 수행할 때의 화면이다.

**③ 최상위 `Tasks` (프로젝트 횡단)**

여기서는 **사람 컬럼을 제공하지 않는다.** 워크스페이스 전원이 컬럼이 되면 실제로 폭주한다.
→ 리스트 뷰 + 필터(프로젝트/담당자/상태/마감)로 제공한다.

### 두 보드가 지켜야 할 단 하나의 규칙

> **보드는 두 개, `status` 필드는 하나.**
> 배정 보드와 내 업무 보드는 **같은 Task 행을 다른 축으로 투영한 두 개의 뷰**다. 상태를 두 벌로 관리하지 않는다.

이 규칙을 어기면 즉시 무너지는 것들:
- 팀원이 `진행중 → 리뷰`로 옮겨도 Admin 쪽에 반영되지 않는다 → 리뷰 요청을 아무도 모른다
- 대시보드 "리뷰 대기" 위젯이 **어느 쪽 상태를 읽어야 할지** 정할 수 없다
- "완료 확정은 Admin이 한다"(D-007)가 **성립 불가능**해진다

화면은 여전히 완전히 다르다. 밑에 깔린 진실만 하나면 된다.

### 정체(stale) 감지 — 캘린더가 아니라 카드에서 해결한다

"3일째 붙잡고 있다"는 **캘린더가 알 수 없는 정보**다.
캘린더가 아는 것은 `startDate` / `dueDate` = **계획**이고, 필요한 것은 `status_changed_at` 이후 경과 시간 = **실제**다.
마감이 다음 주인 업무를 3일째 진행중으로 방치해도 캘린더에는 아무 이상이 없어 보인다.

> **`Task.status_changed_at` 을 두고, 카드에 경과일을 표시한다.**
> `🟡 진행중 · 3일` / 임계 초과 시 `🔴 지연`

- 임계값 기본: `in_progress` 5일 초과, `in_review` 2일 초과 (Settings에서 조정)
- 캘린더는 **계획을 보는 화면**으로 유지한다. 정체 감지를 캘린더에 얹지 않는다.
- 근거: "누가 막혀 있나"는 배정 보드를 보는 중에 떠오르는 질문이다. 답을 위해 화면을 옮기고 두 데이터를 머릿속에서 조인하게 만드는 것은 §2 "불필요한 클릭 최소화" 위반이다. 해결 비용도 **화면 하나 vs 뱃지 한 줄**로 비대칭이다.

### 6.2 Dashboard

**전체 보기 (Lead 기본값 — 범위는 "내가 Lead인 프로젝트들". 워크스페이스 Admin은 전 프로젝트)**

| 위젯 | 답하는 질문 |
|---|---|
| 리뷰 대기 | 내가 지금 확인해줘야 할 게 뭐지? |
| 지연 업무 | 뭐가 늦고 있지? |
| 팀원별 진행중 업무 수 | 누가 과부하지? |
| 진행중 프로젝트 + 진행률 | 프로젝트들이 어디까지 왔지? |
| 이번주 일정 | 이번주에 뭐가 끝나야 하지? |

> ⚠️ 원문의 **"팀원 업무량"** 위젯은 정의를 바꿨다. 원문은 `estimatedHours` 기반을 암시하는데, 소규모 팀은 그 필드를 채우지 않는다. **아무도 안 채우는 필드에 기반한 위젯은 거짓말을 한다.** → **진행중 Task 개수**로 대체한다 (§8 참조).

**내 업무 보기 (전원 사용 — Member 기본값, Lead·Admin도 동일하게 사용)**

| 위젯 | 답하는 질문 |
|---|---|
| 오늘 할 일 | 지금 뭐부터 하지? |
| 내 진행중 업무 | 내가 붙잡고 있는 게 뭐지? |
| 이번주 마감 | 언제까지 뭐가 필요하지? |
| 내 프로젝트 | 나는 어디에 속해 있지? |

**빈 상태 설계 (필수)**
데이터가 없을 때 각 위젯은 회색 박스가 아니라 **다음 행동 버튼**을 보여준다.
예: *"아직 배정된 업무가 없어요 → 업무 만들기"*

### 6.3 Task 상세

Task 하나가 열렸을 때 반드시 있어야 하는 것:
- 제목 · 설명 · 프로젝트 · 담당자 · 상태 · 우선순위 · 마감일
- **댓글 / 활동 로그** ← 원문에 없다. **이게 없으면 논의가 카톡으로 나간다. 제품의 존재 이유가 무너진다. v1 필수.**
- 첨부파일 (v1.1)

### 6.4 알림 (원문에 없음 — v1 필수)

배정이 핵심 행동인데 **배정됐다는 사실을 모르면 제품이 동작하지 않는다.**

| 트리거 | 채널 |
|---|---|
| 나에게 업무가 배정됨 | 인앱 + **푸시** |
| 내 업무에 댓글/멘션 | 인앱 + **푸시** |
| 리뷰 요청이 왔다 → **그 프로젝트의 Lead 전원**에게 | 인앱 + **푸시** |
| 마감 1일 전 / 마감 초과 | 인앱 + 푸시 |
| 워크스페이스 초대 | **이메일** (이때만) |

**이메일 알림은 만들지 않는다 (D-019a).** PWA 푸시가 있으면 이메일은 중복이고, 두 채널로 같은 걸 두 번 받으면 **둘 다 무시하게 된다.** 이메일은 로그인 이전에만 필요하므로 **초대 메일 하나면 충분하다.**
→ 발송 인프라(Resend 등) · 템플릿 · 수신 설정 화면이 통째로 빠진다.

### 6.5 모바일 — PWA로 간다 (D-019)

*"팀원 시나리오는 모바일에서 동작해야 한다"*(§2)를 진짜로 지키려면 반응형만으로는 부족하다. **배정 사실을 즉시 알리는 것**이 이 제품의 생명선인데(§6.4), 브라우저 탭을 열어야만 알 수 있으면 알림이 아니다.

**PWA는 한 덩어리가 아니다. 3단계로 나누고, v1은 L2까지 간다.**

| | 내용 | v1 |
|---|---|---|
| **L1 설치** | `manifest.json` + 아이콘 + 반응형. 홈 화면에 추가되고 앱처럼 전체화면으로 열림 | ✅ |
| **L2 푸시** | Web Push. 배정·리뷰요청·멘션이 폰 알림으로 즉시 도착 | ✅ |
| **L3 오프라인** | Service Worker 캐시 + 오프라인 상태변경 후 동기화 | ❌ **제외** |

**L3를 빼는 이유**
- 오프라인 쓰기는 **동기화 충돌 처리**를 요구한다 (지하철에서 `리뷰`로 옮겼는데 그 사이 Lead가 `완료` 처리한 경우 등). 이건 제품 하나 분량의 난이도다.
- 개발팀은 사실상 항상 온라인이다. **실제로 겪지 않는 문제**다.
- 더 나쁜 건, 캐시 전략을 잘못 짜면 **오래된 보드를 보여준다.** 업무 관리 도구에서 stale 데이터는 오프라인 지원보다 훨씬 해롭다.

> **캐시 원칙: 데이터(보드·업무·댓글)는 절대 캐시하지 않는다. 앱 셸(JS/CSS/아이콘)만 캐시한다.**

**⚠️ iOS 제약 — 도입 전에 팀에 공지해야 한다**
- iOS는 **홈 화면에 추가한 경우에만** 웹 푸시가 동작한다 (iOS 16.4+). 사파리 탭에서는 절대 안 온다.
- 즉 **iOS 팀원은 "홈 화면에 추가" 를 반드시 해야 알림을 받는다.** 온보딩에 이 안내 화면을 넣는다.
- 알림 권한 요청은 사용자 제스처 안에서만 가능하다 → 첫 진입 시 자동 팝업 금지. **"알림 켜기" 버튼**을 명시적으로 둔다.

## 7. 스코프

### v1 — MVP (이것만으로 팀이 매일 쓸 수 있어야 한다)
- 로그인 / 워크스페이스 / 멤버 초대
- Projects: CRUD, 멤버 관리, 개요(진행률)
- **Tasks: 배정 보드 + 진행 보드 (드래그), Task 상세, 댓글**

- Settings: 프로필, 멤버 관리, **알림 켜기**
- **Documents: 링크 보관함** (제목 + 외부 링크 + 프로젝트 연결). 에디터 아님 (D-012)
- **PWA (L1 설치 + L2 푸시).** 모바일에서 "내 업무" 조회 + 상태 변경 동작. 오프라인은 제외 (D-019)

### v1.1
- Calendar (Task 마감 + Meeting을 월/주 뷰로)
- Meetings (회의록 + **Action Item → Task 자동 생성**)
- 전역 검색, 필터 저장

### v2 이후
- 프로젝트 리포트 / 번다운
- 파일 첨부, 반복 업무
- ~~문서 에디터~~ — **팀이 실제로 "여기서 바로 쓰고 싶다"고 말하기 전까지 만들지 않는다**

### 🚫 명시적 비목표 (하지 않는다)
위키, 간트 차트, 타임트래킹 자동화, 워크플로우 자동화 빌더, 커스텀 필드, 외부 클라이언트 포털, 실시간 협업 편집
→ 하나라도 손대는 순간 "Notion보다 단순하다"는 약속이 깨진다.

### Documents는 링크 보관함으로 시작한다 ✅ (D-012 확정)

**전제: 이 팀은 이미 Notion을 쓰고 있다.** (2026-07-26 확인) 문서를 옮길 이유가 없다.

```
📚 Documents
┌────────────────────────────────────────┐
│ 마케팅몬스터 기획서    Notion    ↗     │
│ API 명세서            Notion    ↗     │
│ 디자인 시안           Figma     ↗     │
└────────────────────────────────────────┘
[+ 문서 추가]  →  제목 · 링크 · 프로젝트 선택
```

**근거**
1. **팀이 겪는 문제는 "문서를 못 쓴다"가 아니라 "이 프로젝트 문서가 어디 있더라"다.** 링크 보관함으로 100% 해결된다.
2. **문서 에디터는 그 자체로 제품 하나 분량이다.** 리치 텍스트·이미지 업로드·표·코드블록·중첩 리스트·자동 저장·동시 편집 충돌 — 여기 빠지면 Tasks가 완성되지 않는다.
3. *"회사 업무 외 시간에 개발한다"* 는 제약과 정면 충돌한다. **가장 비싼 기능을 가장 먼저 만들면 안 된다.**
4. 개발량 차이: **반나절 vs 수 주.**

**재검토 조건:** 팀이 실제로 "core_task 안에서 바로 쓰고 싶다"고 말하면 그때 에디터를 검토한다. 그 시점엔 Tasks가 이미 돌아가고 있다.

**모델 관련 결정과 근거**

|---|---|

| 영역 | 선택 |
|---|---|

| 드래그 | dnd-kit |

| 배포 | Vercel (SPA rewrite) |
| 구조 | 모노레포 — `apps/web`, `packages/ui`, `packages/types`, `docs` |

### ⚠️ 원문의 Next.js 결정을 뒤집었다 (D-042)

원문은 Next.js를 지정했으나, **설계를 마치고 나니 Next.js를 쓸 이유가 대부분 사라졌다.**

| 근거 | 내용 |
|---|---|
| **API 레이어를 안 만들기로 했다** | [06-API.md](06-API.md) §1 — 클라이언트가 `supabase-js`로 직접 읽고 쓴다. API Routes·Server Actions가 통째로 불필요해졌다 |
| **RSC와 Supabase 인증의 궁합** | 서버 컴포넌트는 localStorage를 못 읽어 `@supabase/ssr` 쿠키 세션 + 갱신 미들웨어가 필요하다. 저녁 시간을 서버-클라이언트 경계 디버깅에 쓸 수 없다 |
| **PWA 제어권** (결정적) | D-019b가 *"데이터는 캐시 금지, 앱 셸만 캐시"* 라는 정밀한 전략을 요구한다. `vite-plugin-pwa`는 이 제어가 명확하다 |
| **D-031이 오히려 쉬워진다** | react-router의 `backgroundLocation` 이 *"어디서 왔는가"* 그 자체다. Next의 `(.)` 폴더 규약보다 명시적이다 |
| **D-035와 TanStack Query** | Realtime을 껐으므로 포커스 복귀 시 재조회가 필요한데, 그게 `refetchOnWindowFocus` 기본 동작이다 |
| **로그인 뒤에만 존재하는 사내 도구다** | SEO·공개 페이지·서버 전용 시크릿 API — Next.js를 택할 세 가지 이유가 모두 해당 없다 |

**성능 목표는 그대로 만족한다.** 셸(즉시) + 번들 ~200KB(300ms) + 서울 리전 쿼리(50~100ms) = **1초 미만.** 재방문부터는 서비스 워커가 앱 셸을 캐시해 더 빨라진다.
**Vercel 배포도 동일하다** — `vercel.json` 에 SPA rewrite 한 줄이면 된다.

> **Next.js로 되돌릴 조건:** 공개 랜딩 페이지·SEO가 필요해지거나, 서버에서만 접근할 시크릿을 쓰는 API가 생길 때.

**제약 조건 (설계 판단에 실제로 영향을 준다)**
- 개발 시간은 **회사 업무 외 시간**뿐이다 → 기능 하나의 기회비용이 매우 크다.
- **실사용 제품**이다 → 데이터 유실·권한 누수는 용납되지 않는다. Supabase **RLS를 처음부터** 건다.
- ⚠️ **권한 판정이 2단이라 RLS가 한 단계 복잡해진다.** 모든 Task 정책은 `project_members` 조인을 타야 한다.
  → `is_project_lead(project_id, user_id)` / `is_project_member(project_id, user_id)` **Postgres 함수 2개로 추출**해서 모든 정책이 이것만 호출하게 한다. 정책마다 조인을 복붙하면 반드시 어긋난다.
- 팀 규모가 작다 → 실시간 동기화는 **v1에서 필수 아님**(D-035). 낙관적 업데이트 + **포커스 복귀 시 재조회**로 충분하다.
- **서버가 없다**(D-042) → `service_role` 키가 프론트엔드 저장소에 존재하지 않는다. 실수로 노출할 경로 자체가 사라진다.

## 12. 마일스톤 — 날짜가 아니라 순서로 관리한다 (D-020)

**마감일을 박지 않는다.** 업무 외 시간에 개발하고, 그때까지 Notion이라는 폴백이 있으므로 날짜는 지켜지지 않을 뿐 아니라 지킬 필요도 없다.

**대신 순서를 고정한다.** 날짜가 없을 때 위험한 건 지연이 아니라 **스코프가 조용히 늘어나는 것**이므로, 각 마일스톤에 *"여기서 멈추고 다음으로 간다"* 는 완료 조건을 건다.

| | 목표 | 완료 조건 (이걸 넘기면 다음으로) |
|---|---|---|
| **M1** | 뼈대 | 로그인 → 프로젝트 생성 → Task 생성 → 배정 보드에서 드래그 배정이 **끝까지 동작** |
| **M2** | 루프 완성 | 팀원이 상태를 바꾸고 → Lead가 완료 확정하고 → **알림이 폰에 온다** |
| **M3** | 실사용 진입 | 대시보드 · 댓글 · Documents 링크. **여기서 실제 프로젝트 1개를 올린다** |
| **M4** | 전환 | 팀 전체 투입. Notion은 문서 전용으로 축소 |

> **도그푸딩 조건: M2가 끝나면 그 주에 내 업무만이라도 여기에 옮긴다.**
> 완성된 다음에 쓰기 시작하면 잘못된 설계를 끝까지 안고 간다. **M3를 기다리지 않는다.**

**M4(팀 전체 투입) 전에 반드시 확인할 것**
- iOS 팀원 전원 "홈 화면에 추가" + 알림 권한 허용 (§6.5)
- 데이터 백업 동작 확인 — **실사용 데이터가 들어간 순간부터 유실은 되돌릴 수 없다**
