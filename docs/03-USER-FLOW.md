## 1. 이 문서의 검증 기준

Foundation §1: *"core_task의 승부처는 기능 수가 아니라 **입력 비용을 얼마나 낮추느냐**다."*

그래서 이 문서는 각 흐름마다 **클릭 수를 세고, 목표치와 비교한다.** 목표를 넘으면 흐름을 다시 설계한다.

| 흐름 | 빈도 | 목표 클릭 수 |
|---|---|---|
| **F1** 업무 배정 (Lead) | 주 수십 회 | **≤ 2** |
| **F2** 업무 수행 (Member) | 일 수 회 | **≤ 2** |
| **F3** 리뷰 → 완료 확정 (Lead) | 일 수 회 | **≤ 2** |
| F4 업무 생성 | 일 수 회 | ≤ 3 |
| F5 미배정 가져가기 | 주 수 회 | ≤ 2 |
| F0 온보딩·초대 | 평생 1회 | ≤ 6 |

**그리고 각 흐름마다 "여기서 끊기면 카톡으로 샌다"는 지점(🚨)을 표시한다.** Foundation §1의 실패 원인을 흐름 단위로 추적하기 위해서다.

## 2. F0 · 온보딩과 초대

### F0-A. 창업자 (최초 1인)

```
   /signup
     │  ① 이메일·비밀번호 입력 또는 Google
     ▼
   /onboarding/workspace          ← 워크스페이스 없으면 강제 진입
     │  ② 회사 이름 입력 → [만들기]
     │     ⤷ `개인 업무` 프로젝트 자동 생성 (D-023)
     ▼
   /                              ← 대시보드 (프로젝트 0개 상태)
     │  "첫 프로젝트를 만들어보세요"
     │  ③ [프로젝트 만들기]
     ▼
   /projects?new=1  (모달)
     │  ④ 이름만 입력 → [만들기]
     ▼
   /projects/[id]                 ← 개요. 생성자는 자동 Lead
        "팀원 추가"  "첫 업무 만들기"
```
**클릭 4회.** ✅ 목표 이내

> 💡 **`개인 업무` 프로젝트가 이 시점에 이미 있다는 게 중요하다.** 프로젝트를 아직 안 만든 사람도 업무를 적을 곳이 있다. 첫날 아무것도 못 하는 상태를 만들지 않는다.

### F0-B. 초대받은 팀원

```
   📧 초대 메일 ─── [수락하기]
     │                     (이메일이 필요한 유일한 지점 — D-019a)
     ▼
   /invite/[token]
     │
     ├─ 계정 없음 → /signup → 가입 → 자동 합류 ──┐
     ├─ 계정 있음 → /login → 로그인 → 자동 합류 ─┤
     └─ 로그인 상태 → 즉시 합류 ─────────────────┤
                                                 ▼
                                              /  대시보드
                                                 │
                        ┌────────────────────────┴───────────┐
                        │ 소속 프로젝트 있음 → 정상 대시보드    │
                        │ 소속 프로젝트 0개 → "관리자에게 요청" │
                        └────────────────────────────────────┘
                                                 │
                                                 ▼
                                   📱 "홈 화면에 추가" 안내 (모바일 1회)
                                                 │
                                                 ▼
                                        [알림 켜기] → 권한 요청
```

**🚨 끊기는 지점: 초대는 수락했는데 프로젝트에 안 넣어준 경우.**
팀원은 로그인해서 빈 화면을 보고 나가버린다. 그리고 다시 안 들어온다.

**대응 ✅ 확정 (D-033 · US-102 AC-8)**
> **초대 시점에 프로젝트를 함께 지정한다.** *"[이메일] 을 [마케팅몬스터] 프로젝트에 초대"*
> 워크스페이스 초대와 프로젝트 배치를 두 단계로 나누면, 두 번째 단계가 잊힌다.
> 프로젝트를 안 고르고 초대하는 것도 가능하지만, **그 경우 초대 목록에 `⚠️ 프로젝트 미배치` 로 표시**해 잊히지 않게 한다.

**🚨 두 번째 끊기는 지점: iOS 사용자가 홈 화면 추가를 안 함.**
→ 푸시가 영영 안 온다 (Foundation §6.5). 알림 없는 배정은 배정이 아니다.

**대응**
- 안내를 닫아도 **알림 권한이 미설정인 동안 대시보드 상단에 얇은 배너를 유지**한다.
- 배너는 "알림을 켜면 업무 배정을 바로 알 수 있어요" 로 **이득을 말한다.** "설정하세요" 라고 하지 않는다.

## 3. F1 · 업무 배정 ⭐ (Lead) — 제품의 심장

> **이 흐름이 무너지면 제품 전체가 무너진다** (PRD §2 S1).
> Foundation §1: *"업무 배정이 카톡·구두·회의로 흩어진다"* 를 정면으로 푸는 흐름이다.

### 정상 경로

```
   사이드바 [최근 프로젝트 > 마케팅몬스터]     ← 1클릭 (D-030 덕분)
     ▼
   /projects/[id]/board                       ← 배정 보드
     │
     │   미배정        김프론트       이백엔드
     │  ┌────────┐   ┌──────────┐  ┌────────┐
     │  │결제 연동│──┐│로그인 API │  │스키마  │
     │  └────────┘  │└──────────┘  └────────┘
     │              │
     │              └─ ② 드래그 & 드롭
     ▼
   ┌─ 마감일 팝오버 (마감일이 비어 있을 때만) ─┐
   │  언제까지?                                │
   │  [오늘] [내일] [이번주 금] [다음주 금]      │  ← ③ 퀵칩 1탭
   │  [직접 선택]        [나중에 정하기]        │
   └──────────────────────────────────────────┘
     ▼
   ✅ 배정 완료
     ├ assigneeId 설정 (status 변경 없음 — D-018a)
     ├ 담당자에게 푸시 알림
     └ Activity 기록
```

**클릭 수**

| 상황 | 클릭 | 판정 |
|---|---|---|
| 마감일이 이미 있음 | **1회** (드래그) | ✅ |
| 마감일 없음 → 퀵칩 | **2회** (드래그 + 칩) | ✅ 목표 이내 |
| 마감일 없음 → 직접 선택 | 3~4회 | ⚠️ 허용하되 기본 경로 아님 |

> **퀵칩이 이 흐름의 성패를 가른다.** 달력 위젯을 열게 하면 배정 하나에 4클릭이 되고, Lead는 "그냥 카톡으로 말하지" 로 돌아간다. 퀵칩 4개(`오늘`/`내일`/`이번주 금`/`다음주 금`)가 실무 마감일의 대부분을 덮는다.

### 분기와 예외

| 분기 | 처리 |
|---|---|
| 드래그 실패 (네트워크) | 카드 원위치 + 토스트. **낙관적 업데이트라 화면은 이미 옮겨져 있었다가 되돌아온다** |
| `나중에 정하기` 선택 | 배정은 되고 `⚠️ 마감일 없음` 뱃지. 프로젝트 개요와 대시보드에 건수 집계 |
| 이미 남에게 배정된 카드를 다른 사람에게 | 허용 (Lead 권한). 이전 담당자에게도 알림 |
| Member가 드래그 시도 | **드래그 자체가 비활성.** 미배정 컬럼의 카드만 본인 쪽으로 가능 (F5) |
| 담당자를 떼고 싶음 | 카드를 `미배정` 컬럼으로 드래그. 마감일은 유지 (EC-19) |

### 🚨 이 흐름에서 카톡으로 새는 지점

| 위험 | 원인 | 대응 |
|---|---|---|
| **"이거 왜 나한테 왔지?"** | 배정만 되고 맥락이 없음 | Task 설명 또는 댓글. 배정 알림에 **Task 제목 + 프로젝트명 + 마감일**을 함께 실어보낸다 |
| **"급한 거야?"** | 우선순위가 안 보임 | 카드에 우선순위 표시 (US-402 AC-7) |
| **"이거 언제까지야?"** | 마감일 없이 배정 | 마감일 팝오버 (US-304). **이 질문을 없애려고 만든 장치다** |

## 4. F2 · 업무 수행 (Member)

### 4-A. 데스크톱

```
   푸시 알림 "새 업무가 배정되었습니다"
     │  ① 클릭
     ▼
   /tasks/[taskId]  (전체 페이지 — 알림 진입이므로, D-031)
     │  내용 확인
     │  ② [시작하기]  →  status: todo → in_progress
     ▼
   ...작업...
     │
     ▼
   /tasks  내 업무 보드
     │  ③ 카드를 [리뷰중] 컬럼으로 드래그
     ▼
   ✅ 리뷰 요청 = 상태 변경 그 자체 (US-502 AC-1)
     └ 그 프로젝트 Lead 전원에게 푸시
```
**작업 시작 2클릭 / 리뷰 요청 1클릭.** ✅

> 💡 **"리뷰 요청" 버튼을 따로 만들지 않았다.** `in_review` 로 옮기는 것이 곧 요청이다. 버튼을 따로 두면 "상태는 바꿨는데 요청은 안 누른" 상태가 생기고, 그 틈이 정확히 카톡이 파고드는 자리다.

### 4-B. 모바일 (출근길 시나리오)

```
   하단탭 [📋 내 업무]
     ▼
   ┌────────────────────────────────┐
   │ [예정 3][진행중 2][리뷰중 1][완료]│  ← 상태 탭 (칸반 아님, D-026)
   ├────────────────────────────────┤
   │ 로그인 API 연동      마케팅몬스터 │
   │ 🟡 진행중 · 3일        ~7/28     │
   │                    [리뷰 요청]  │  ← ② 액션 버튼 1탭
   ├────────────────────────────────┤
   │ 소셜 로그인          마케팅몬스터 │
   │ 🔵 예정              ~7/30      │
   │                    [시작하기]   │
   └────────────────────────────────┘
```

**모바일에서 상태 변경은 드래그가 아니라 버튼이다.** 현재 상태에 따라 **다음 행동 하나만** 노출한다.

| 현재 | 노출 버튼 |
|---|---|
| `todo` | `시작하기` |
| `in_progress` | `리뷰 요청` |
| `in_review` | (없음 — 대기 중) |
| `done` | (없음) |

> **버튼을 하나만 두는 이유:** 폰에서 선택지가 여럿이면 오탭이 난다. 그리고 실제로 다음 행동은 거의 항상 하나다. 되돌리기가 필요하면 Task 상세로 들어간다.

### 🚨 끊기는 지점

| 위험 | 대응 |
|---|---|
| **막혔는데 아무도 모름** | 정체 임계 초과 시 🔴 (D-027) + Lead 대시보드 `지연 업무` 위젯 |
| **막힌 이유를 말할 곳이 없음** | Task 댓글. **이게 없으면 100% 카톡으로 간다** (D-010) |
| 업무를 못 하겠음 (반납) | **불가** (EC-6). 댓글로 남기고 Lead가 재배정한다 |

## 5. F3 · 리뷰 → 완료 확정 (Lead)

> Foundation D-007의 *"완료 확정은 Lead가 한다"* 를 실제 동작으로 만드는 흐름.

```
   푸시 "김프론트님이 리뷰를 요청했습니다"
     │  ① 클릭
     ▼
   /tasks/[taskId]
     │
     ├─ ② [완료 확정] ──────────────► done
     │      └ completedAt 기록, 담당자에게 알림
     │
     └─ ② [반려] ───────────────────► in_progress
            │
            ▼
        ┌─ 사유 입력 (필수) ─────────┐
        │ 왜 되돌리나요?             │  ← ③ 입력
        │ [____________________]     │
        │            [반려하기]      │
        └───────────────────────────┘
            └ 사유가 Task 댓글로 저장 + 담당자 알림
```

**완료 확정 2클릭 / 반려 3클릭 (사유 포함).** ✅

### 대시보드에서 바로 처리하는 더 짧은 경로

```
   /  대시보드 ?tab=all
     │
     │  ┌─ 리뷰 대기 (3) ────────────────┐
     │  │ 로그인 API   김프론트  [확인] │  ← ① 여기서 바로 완료 확정
     │  │ 배너 교체    박디자인  [확인] │
     │  └──────────────────────────────┘
     ▼
   ✅ 1클릭
```
**Lead가 가장 자주 하는 행동이라 클릭 깊이를 0으로 만들었다** (US-702 AC-4).

### 왜 반려 사유를 필수로 했나

**사유 없는 반려는 반드시 카톡을 부른다.** *"어? 왜 반려됐지?"* → 담당자가 Lead에게 물어봄 → 대화가 도구 밖에서 일어남 → **Foundation §1의 실패 조건 그대로.**

입력 한 번의 비용으로 대화 하나를 도구 안에 붙잡아 두는 거래다.

### 분기

| 분기 | 처리 |
|---|---|
| Lead가 자기 Task를 확정 | **허용** (EC-5). 막으면 Lead 업무가 영영 리뷰중에 갇힌다. Activity에는 남는다 |
| Lead가 여러 명 | **먼저 처리한 사람이 확정.** 나머지 Lead의 알림은 읽음 처리 |
| 확정 후 문제 발견 | Lead가 `done → in_progress` 되돌리기 (§ 상태 전이표) |
| WS Admin이 Lead 대신 확정 | 허용 (D-016d). Activity에 **"(관리자 권한)"** 표기 (US-603 AC-4) |

## 6. F4 · 업무 생성 · F5 · 가져가기

### F4. 업무 생성 (누구나)

```
   /projects/[id]/board
     │  ① 컬럼 하단 [+ 업무 추가]
     ▼
   ┌─ 인라인 입력 (모달 아님!) ──┐
   │ [제목을 입력하세요_______] │  ② 제목 입력
   └────────────────────────────┘
     │  ③ Enter
     ▼
   ✅ 생성 완료. 입력창은 그대로 남아 다음 업무를 바로 입력할 수 있다.
```
**3클릭 (사실상 타이핑 + Enter).** ✅

**생성 기본값**

| 만든 사람 | assigneeId | status |
|---|---|---|
| Lead가 `미배정` 컬럼에서 | `NULL` | `todo` |
| Lead가 특정 사람 컬럼에서 | **그 컬럼의 사람** | `todo` |
| Member가 | **본인** | `todo` |

> 💡 **어느 컬럼에서 눌렀는지가 곧 담당자다.** 담당자 선택 드롭다운을 없앨 수 있는 이유다.
> ⚠️ 단, 사람 컬럼에서 만들면 곧 "배정된 Task"가 되므로 **마감일 팝오버가 뜬다** (US-304 AC-2).

### F5. 미배정 가져가기 (Member) — D-024

```
   /projects/[id]/board  또는  /tasks?view=list
     │
     │  미배정 컬럼
     │  ┌──────────────┐
     │  │ 배너 교체     │
     │  │ [내가 할게요] │  ← ① 1클릭
     │  └──────────────┘
     ▼
   ┌─ 마감일 입력 (필수 — 건너뛰기 없음) ─┐
   │ 언제까지 하실 건가요?                │  ← ② 퀵칩
   │ [오늘][내일][이번주 금][다음주 금]     │
   └─────────────────────────────────────┘
     ▼
   ✅ assigneeId = 본인
     └ Lead에게 알림 "○○님이 '배너 교체'를 가져갔습니다"
```
**2클릭.** ✅

> ⚠️ **여기서만 `나중에 정하기` 를 안 준다** (US-403 AC-5).
> Lead가 배정할 때는 *"남에게 주는 기한"* 이라 유예가 필요할 수 있지만, 가져가기는 **본인이 스스로 하는 약속**이다. 스스로 한 약속에 기한이 없으면 그건 약속이 아니다.

**금지 동작**

| 시도 | 결과 |
|---|---|
| 남에게 배정된 Task 가져가기 | **불가** (EC-7). 버튼 자체가 없음 |
| 내 Task를 미배정으로 반납 | **불가** (EC-6) |

## 7. F6 · 담당자 이탈 (US-204)

**사람이 나가는 건 예외가 아니라 정기적으로 일어나는 일이다.** 흐름으로 설계해 둔다.

```
   /projects/[id]/settings
     │  ① [김프론트 · 제거]
     ▼
   ┌─ 확인 (영향 범위를 먼저 보여준다) ────────┐
   │ 김프론트님을 마케팅몬스터에서 제거합니다   │
   │                                          │
   │ ⚠️ 담당 중인 미완료 업무 4건이            │
   │    미배정으로 돌아갑니다.                 │
   │      · 로그인 API 연동   🟡 진행중        │
   │      · 소셜 로그인       🔵 예정          │
   │      · ... 외 2건                        │
   │                                          │
   │              [취소]  [제거하기]           │
   └──────────────────────────────────────────┘
     ▼
   ✅ 처리
     ├ 미완료 Task → assigneeId = NULL, **status는 유지**
     ├ 완료 Task → 담당자 그대로 (기록이므로, EC-4)
     └ Lead 전원에게 알림 "업무 4건이 미배정되었습니다"
     ▼
   배정 보드 미배정 컬럼
     ┌──────────────────┐
     │ 로그인 API 연동   │
     │ 🟡 진행중 · 3일   │  ← status 유지가 여기서 값을 한다
     └──────────────────┘
        "어디까지 됐는지"를 알고 재배정할 수 있다
```

> 💡 **`status` 를 초기화하지 않는 것이 이 흐름의 핵심이다.**
> `todo` 로 되돌리면 *"처음부터 다시"* 라는 잘못된 신호를 준다. 진행중이던 일은 진행중인 채로 미배정 컬럼에 남아야, 새 담당자가 이어받을지 처음부터 할지 판단할 수 있다.

**막히는 경우**

| 시도 | 결과 |
|---|---|
| 마지막 Lead 제거 | **차단** (EC-1) — "프로젝트에는 최소 1명의 Lead가 필요합니다" |
| 마지막 Owner 제거 | **차단** (EC-14) |
| 워크스페이스에서 제거 | 소속 **모든 프로젝트**에 위 흐름 적용 (EC-3) |

## 8. 알림에서 시작하는 모든 흐름

**알림은 별도 흐름이 아니라 다른 흐름의 진입점이다.** 여기서 정리한다.

| 알림 | 클릭 시 도착지 | 이어지는 흐름 |
|---|---|---|
| 새 업무가 배정됨 | `/tasks/[taskId]` (전체) | **F2** 수행 |
| 리뷰 요청이 왔다 | `/tasks/[taskId]` (전체) | **F3** 완료 확정 |
| 완료 확정 / 반려됨 | `/tasks/[taskId]` (전체) | (반려면 F2 재수행) |
| 댓글 / 멘션 | `/tasks/[taskId]` (댓글 위치로 스크롤) | 대화 |
| 담당자 이탈로 미배정 발생 | `/projects/[id]/board?filter=unassigned` | **F1** 재배정 |
| 마감 임박 / 초과 | `/tasks/[taskId]` | F2 |

**규칙**
1. **모든 알림은 반드시 특정 화면으로 착지한다.** 목록으로 보내는 알림은 만들지 않는다 — "그래서 뭘 보라는 거지" 가 되면 안 누르게 된다.
2. 알림 클릭 = **읽음 처리**.
3. 이미 처리된 알림(예: 다른 Lead가 먼저 확정)을 눌러도 오류를 내지 않는다. Task 상세를 보여주고 현재 상태를 그대로 표시한다.
4. **본인이 일으킨 이벤트는 본인에게 알리지 않는다** (US-801 AC-2).
