## 0. 한 줄 요약

**"한눈에"는 하나의 요구가 아니라 세 개의 다른 질문이었다.**

| 질문 | 답하는 화면 | 상태 |
|---|---|---|
| 언제 뭐가 몰려 있나 | **캘린더** | 신설 (§3) |
| 프로젝트가 일정대로 가나 | **프로젝트 개요 한 줄** | 확장 (§5) |
| 누가 쏠려 있나 | 캘린더 옆 담당자별 건수 | 신설 (§4) |
| 업무 사이 선후행 | — | **계속 안 만든다** (§1) |

그리고 이 셋 전부의 전제가 하나 빠져 있었다 — **시작일을 입력할 방법이 없다** (§2).

## 1. 간트는 계속 안 만든다

[Foundation §10](00-FOUNDATION.md#L431) 의 🚫 명시적 비목표에 이미 들어 있다.
이번 논의에서 **유지하기로 확인했다** (2026-07-28).

결정 로그만으로 닫지 않고, 데이터 쪽 근거를 남긴다 — 나중에 다시 꺼내질 질문이기 때문이다.

**간트의 존재 이유는 선후행 의존관계다.** "A가 끝나야 B가 시작된다" 를 그려서
한 칸이 밀리면 뒤가 통째로 밀리는 것을 보여주는 것. `tasks` 에는 의존관계가 없고,
넣을 계획도 없다.

**의존관계 없는 간트는 마감일 막대그래프다.** 그건 캘린더가 더 싸고 더 잘한다 —
같은 정보를 주면서 "이번 주"라는 사람이 실제로 쓰는 단위에 맞춰준다.

> ⚠️ **되살아날 조건**: 팀이 "이거 끝나야 저거 시작인데 그게 안 보인다" 를
> 두 번 이상 말하면 그때 의존관계 모델부터 다시 검토한다. 그 전에는 아니다.

## 2. 시작일을 실제로 입력할 수 있게 한다 — US-304 회수

### 2.1 발견

[US-304 AC-4·5](01-PRD.md#L258) 는 이미 정확히 이렇게 적혀 있다.

> **`startDate` 는 항상 선택이다.** 비어 있으면 `in_progress` 로 처음 전환된 날짜가
> 자동으로 기록된다. 즉 `startDate` 는 *계획된 시작일*이자, 없으면 *실제 시작일*이 된다.
> **나중에 수동으로 덮어쓸 수 있다.**
>
> **`startDate > dueDate` 인 조합은 저장할 수 없다. 입력 시점에 막는다.**

**AC-4 의 "덮어쓸 수 있다" 와 AC-5 가 구현되지 않았다.** M1 은 ✅ 로 닫혀 있다.

| 층 | 상태 |
|---|---|
| 컬럼 `tasks.start_date` | ✅ 있다 |
| CHECK `start_date <= due_date` | ✅ 있다 ([05-DB.md:216](05-DB.md)) |
| 자동 기록 트리거 (D-021c) | ✅ 있다 |
| **생성 모달 입력** | ❌ 없다 — 제목·마감일·우선순위·설명만 받는다 |
| **상세 편집** | ❌ 없다 — [task-detail.tsx:188](../apps/web/src/features/task/task-detail.tsx) 이 읽기 전용 텍스트로 뿌린다 |
| **`useUpdateTask` 허용 필드** | ❌ 없다 — `title·description·due_date·priority` 뿐 |

> 컬럼도 제약도 트리거도 다 있는데 **입구만 없었다.**
> US-202(프로젝트 멤버 관리)를 M3 에서 회수한 것과 같은 종류다.
> 혼자 쓰는 동안에는 드러나지 않는다 — 혼자면 "오늘 시작" 말고 다른 걸 쓸 일이 없다.

### 2.2 왜 지금 필요한가

사용자 표현 그대로: **"업무가 매일 오늘만 생기는 게 아니고, 오늘부터 시작하는 것도 아니다."**

다음 주 월요일에 시작할 일을 오늘 만들면, 지금은 그 사실을 적을 데가 없다.
마감일만 있으면 캘린더에서 그 업무는 **마감일 하루에만 존재**한다 —
"이번 주에 뭘 하고 있나" 에 답할 수 없다.

### 2.3 새 컬럼을 만들지 않는다

`planned_start` 를 따로 두는 안은 **채택하지 않는다.**

| | 한 컬럼 (채택) | 두 컬럼 |
|---|---|---|
| 의미 | "시작일" 하나. 정했으면 계획, 안 정했으면 실제 착수일이 채워진다 | `planned_start` = 계획 / `start_date` = 실제 |
| 입력 | 0개 추가 | 1개 추가 |
| 근거 | **US-304 AC-4 가 이미 이렇게 정의해 뒀다** | 정확하지만 Foundation §1 "입력 비용" 과 충돌 |

**실제 착수 시점을 잃지 않는다.** 계획 시작일을 넣어두면 자동 기록은 건너뛰지만
(`if new.start_date is null`), 실제로 언제 `in_progress` 가 됐는지는
`activities` 의 `status_changed` 행과 `status_changed_at` 에 그대로 남는다.
**한 컬럼에 두 의미가 아니라, 실제 착수는 애초에 다른 곳에 있다.**

### 2.4 만들 것

| # | 내용 |
|---|---|
| 1 | **생성 모달에 시작일** — 마감일과 같은 자리, 같은 퀵칩(D-034). 선택 |
| 2 | **상세에서 시작일 편집** — 마감일과 같은 인라인 편집 (US-601 AC-3) |
| 3 | **`useUpdateTask` 에 `start_date` 추가** |
| 4 | **입력 시점 검증** (AC-5) — 시작일 > 마감일이면 저장 버튼을 막고 그 자리에서 말한다 |
| 5 | **[US-302 AC-1 문구 수정](01-PRD.md#L279)** — 수정 가능 필드에 시작일이 빠져 있다. US-304 AC-4 와 서로 어긋난 상태다 |

### 2.5 ⚠️ 에러 코드가 하나 필요하다

CHECK 제약 `start_date <= due_date` 는 위반 시 Postgres 코드 `23514` 를 던진다.
[parseDbError](../apps/web/src/lib/errors.ts) 는 `CODE: 설명` 형태만 읽으므로
지금 상태로는 `UNKNOWN` → *"잠시 후 다시 시도해주세요"* 가 뜬다. 틀린 안내다.

**D-057(에러는 코드로 구분한다)에 따라 코드를 하나 늘린다.**

| 코드 | 문구 |
|---|---|
| `INVALID_PERIOD` | 시작일이 마감일보다 늦어요. 날짜를 다시 확인해주세요 |

클라이언트가 먼저 막지만(AC-5), **서버도 판정한다** — 클라이언트 검증은 편의고
불변식은 DB 가 지킨다 (06-API §1).

## 3. 캘린더 뷰 — US-506 (신설)

> 나는 팀원으로서, 이번 주에 내 일이 어떻게 깔려 있는지 한 화면에서 보고 싶다.
> 나는 Lead로서, 다음 주에 마감이 몰려 있는지 미리 알고 싶다.

### 3.1 위치 — `내 업무` 의 세 번째 뷰

```
내 업무          [ 보드 ] [ 리스트 ] [ 캘린더 ]
─────────────────────────────────────────────
필터: 프로젝트 · 담당자 · 상태 · 마감범위     ← 리스트 뷰와 공유
```

**최상위 탭을 새로 만들지 않는다.** IA §4 의 사이드바 3개 · 하단 탭 4개는
"안 쓰는 걸 뺀다"로 지킨 숫자다. 캘린더는 `내 업무`가 답하는 질문의 다른 표현이지
다른 장소가 아니다.

**이 선택이 범위 문제를 지운다.** US-504 에서 만든 담당자 필터가 그대로 붙으므로
"내 것만 볼까 팀 전체를 볼까"를 뷰가 결정하지 않는다 — 필터가 결정한다.

### 3.2 무엇을 놓는가 — **아는 만큼 그린다**

| 데이터 | 렌더 |
|---|---|
| 시작일 + 마감일 | **막대** (시작일 칸 → 마감일 칸) |
| 마감일만 | **점** (마감일 칸 하나) |
| 마감일 없음 | 캘린더에 없다 → 상단 `마감없음 N건` 칩 |

```
8월
 월     화     수     목     금
              1      2      3
       ▐████ 로그인 API ████▌
                    ●결제   ●배너
 6      7      8      9     10
 ●스키마              ▐██ 소셜 ██▌

⚠ 마감없음 3건
```

**모드 토글이 아니다.** 사용자가 "막대 보기/점 보기"를 고르는 게 아니라,
데이터가 있으면 막대가 되고 없으면 점이 된다. 규칙이 하나라 설명이 필요 없다 —
점은 "이 날 마감", 막대는 "이 기간에 한다".

부수 효과가 하나 있는데 의도한 것이다: **시작일을 넣으면 막대가 생긴다.**
채우라고 강요하지 않고, 채우면 보상이 있다.

### 3.3 마감 없는 업무를 숨기지 않는다

캘린더는 계획을 보는 화면이고(D-015), 마감 없는 업무는 계획이 없다.
그래서 격자 안에는 넣지 않는다. **대신 상단에 건수 칩으로 세워둔다** —
안 보이면 방치되고, 방치를 눈에 보이게 하는 것은 이미 US-304 AC-8 이 요구한 바다.
칩을 누르면 리스트 뷰로 그 조건이 걸린 채 넘어간다.

### 3.4 정체 감지를 얹지 않는다

**D-015 를 그대로 지킨다.** "3일째 붙잡고 있다"는 캘린더가 알 수 없는 정보고,
그 답은 카드의 경과일 뱃지에 이미 있다. 캘린더 막대를 빨갛게 칠하고 싶어지면
그때 D-015 를 다시 읽는다.

단, **마감이 지난 미완료**는 표시한다 — 그건 계획 대비 사실이고 캘린더가 아는 것이다.

### 3.5 월 / 주 / 모바일

| | |
|---|---|
| 기본 | **월 뷰**. "다음 주에 몰렸나"는 두 주가 한 화면에 있어야 보인다 |
| 주 뷰 | 2순위. 월 뷰에서 한 칸이 3건을 넘으면 그때 필요해진다 |
| 모바일 | 390px 에 7열 격자는 한 칸이 50px 다. **주 뷰를 기본으로** 하거나, 월은 "날짜별 점 개수"만 보여주고 탭하면 그 날 목록을 연다 |

> 모바일 형태는 구현 전에 다시 정한다. 지금 정하면 화면을 안 보고 정하는 것이다.

### 3.6 데이터

새 쿼리가 필요 없다. `v_tasks_enriched` 에 `start_date` · `due_date` · `status` ·
`priority` · `project_name` 이 전부 있고, [use-task-list.ts](../apps/web/src/features/my-tasks/use-task-list.ts)
의 필터가 그대로 쓰인다. **보이는 달의 범위로 `due_date` 를 거는 것만 추가한다.**

⚠️ 막대 때문에 범위 조건이 한 겹 늘어난다. "이 달에 걸치는 업무"는
`due_date` 가 이 달인 것뿐 아니라 **시작일이 이전 달이고 마감일이 다음 달인 것**도 포함된다.
`start_date <= 월말 and (due_date >= 월초 or due_date is null)` 로 잡는다.

## 4. 누가 쏠려 있나 — US-507 (신설)

### 4.1 "과부하"라고 부르지 않는다

정확히 재려면 업무의 **크기**를 알아야 한다. 스토리 포인트도 시간 추정도 없고,
타임트래킹은 [비목표](00-FOUNDATION.md#L431)다. 지금 셀 수 있는 것은 **건수**뿐이다.

건수는 부하의 근사치일 뿐이다 — 3일짜리 하나와 10분짜리 다섯 개가 같아 보인다.
그래서 이름을 낮춘다: **"과부하 판정"이 아니라 "쏠림 보기"다.**
사람이 보고 판단할 재료를 주는 것까지가 이 화면의 일이다.

### 4.2 형태

캘린더 옆(데스크톱) · 위(모바일)에 **보이는 기간의 담당자별 건수** 한 덩어리.

```
이번 달 마감          김프론트 ████████ 8
                    이백엔드 ███ 3
                    박디자인 █ 1
                     미배정  ██ 2
```

- 담당자 필터가 `전체`일 때만 의미가 있다 — 한 명으로 좁히면 막대 하나다
- 이름을 누르면 그 사람으로 필터가 걸린다
- **미배정을 같은 자리에 놓는다.** 아무에게도 안 간 일이 몇 건인지가
  쏠림 판단의 절반이다

### 4.3 v1 범위

캘린더에 **사람별 색을 칠하지 않는다.** 4~20명이면 색이 모자라고,
색으로 사람을 구분하는 순간 상태 5색(D-051)과 충돌한다.
쏠림은 위 건수 막대가 답하고, 캘린더 격자는 시간만 말한다.

## 5. 프로젝트가 일정대로 가나 — US-206 (신설)

### 5.1 이건 캘린더도 간트도 아니다

캘린더는 업무 하나하나를 보여주지 "프로젝트가 늦었나"에 답하지 않는다.
간트는 그걸 하려다 의존관계가 없어서 실패한다. **답은 두 숫자의 비교다.**

```
경과율 = (오늘 - 시작일) / (종료일 - 시작일)      0~1 로 자른다
진행률 = 완료 / 전체                              이미 v_project_stats.progress
```

| 상태 | 조건 | 표시 |
|---|---|---|
| 앞서감 | 진행률 ≥ 경과율 | `기간 60% · 진행 72%` |
| 뒤처짐 | 경과율 − 진행률 > 20%p | `기간 60% · 진행 31%` 🔴 |

프로젝트 개요([overview-page.tsx](../apps/web/src/features/projects/overview-page.tsx))의
진행률 막대 **바로 아래 한 줄**이다. 새 화면을 만들지 않는다.

**저장하지 않는다** (D-009). 둘 다 계산으로 나온다.

### 5.2 ⚠️ 먼저 막힌 것 — 프로젝트 기간을 입력할 수 없다

`projects.start_date` · `end_date` 는 컬럼도 있고 `create_project` RPC 도 받는데,
[생성 다이얼로그가 보내지 않는다](../apps/web/src/features/projects/projects-page.tsx) —
`p_name` · `p_customer` · `p_description` 뿐이다. **수정 화면도 없다.**

그래서 **모든 프로젝트의 기간이 `null` 이고, 이 위젯은 절대 뜨지 않는다.**
US-103 AC-1 이 개인 업무 때문에 한 번도 실행되지 않았던 것과 같은 모양이다.

> 순서상 **프로젝트 기간 입력이 먼저다.** 그게 없으면 §5 는 죽은 코드가 된다.

### 5.3 정직하게 남길 한계

업무가 기간에 균등하게 깔려 있다는 가정이 깔려 있다. 앞이 무겁거나 뒤가 무거운
프로젝트에서는 거짓 경보가 난다. **그래서 색으로 겁주되 판정하지 않는다** —
문구는 "늦었습니다"가 아니라 숫자 두 개를 나란히 보여주는 것으로 끝낸다.

## 6. 비목표 (이번 범위에서 하지 않는 것)

| | 이유 |
|---|---|
| 업무 간 선후행 · 간트 | §1 |

## 8. 순서

| # | 항목 | 왜 이 순서인가 |
|---|---|---|
| 1 | **US-304 회수** — 시작일 입력·편집·검증 + `INVALID_PERIOD` | 캘린더 막대의 전제. 이게 없으면 §3 은 점만 찍는다 |
| 2 | **프로젝트 기간 입력** — 생성/수정 | §5 의 전제. 없으면 죽은 코드 |
| 3 | **캘린더 월 뷰 (데스크톱)** | 본체 |
| 4 | **쏠림 보기** | 캘린더가 있어야 놓을 자리가 생긴다 |
| 5 | **프로젝트 진척 한 줄** | 2번이 끝나 데이터가 쌓이기 시작한 뒤 |
| 6 | **캘린더 모바일** | 데스크톱에서 형태가 확정된 뒤 (§3.5) |

> **1번과 2번은 기능 추가가 아니라 회수다.** 명세엔 있고 입구가 없던 것들이다.
> 새 화면(3~5)보다 먼저 닫는 편이, 캘린더가 빈 격자로 태어나는 것을 막는다.
