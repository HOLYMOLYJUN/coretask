## 1. 이 문서를 읽는 법

- **US-xxx** = 사용자 스토리. 각 스토리는 **수용 기준(AC)** 을 갖는다. AC를 전부 만족하면 그 스토리는 "완료"다.
- **AC는 테스트 가능해야 한다.** "사용하기 편해야 한다" 같은 건 AC가 아니다.
- **🔴 P0** = 이게 없으면 제품이 동작하지 않음 / **🟠 P1** = 없으면 불편하지만 동작함 / **🟡 P2** = 있으면 좋음
- **v1은 P0 전부 + P1 전부**를 포함한다. P2는 여유가 생기면 넣는다.

## 2. v1이 성공했다고 말할 수 있는 조건

Foundation §1의 지표를 **검증 가능한 문장**으로 옮긴 것이다.

| # | 조건 | 측정 방법 |
|---|---|---|
| S1 | Lead가 **주 1회 이상 배정 보드에서 드래그로 배정**한다 | `Activity` 에 `assigned` 이벤트가 주간 1건 이상 |
| S2 | 팀원이 첫 주에 **본인 Task 상태를 직접 1회 이상 변경**한다 | 가입 7일 내 `status_changed` 이벤트 보유 팀원 ≥ 80% |
| S3 | 도입 4주차 **주간 활성 팀원 ≥ 80%** | 주간 로그인 + 액션 1건 이상 |
| S4 | **업무 배정이 카톡으로 나가지 않는다** | 정성 확인 (M4 회고에서 팀에 직접 질문) |

> **S1이 이 제품의 심장이다.** S1이 무너지면 나머지 지표가 좋아도 실패다. 배정이 도구 밖에서 일어나면 데이터 전체가 거짓말이 된다.

## 3. 용어 정의 (이후 모든 문서가 이 단어를 쓴다)

| 용어 | 정의 | 쓰지 않을 말 |
|---|---|---|
| **Workspace** | 회사 하나. 모든 데이터의 최상위 경계 | 조직, 팀스페이스 |
| **Project** | 관리 단위. Task의 필수 소속처 | 보드 |
| **Task** | 실행 단위. 한 사람이 맡는 하나의 일 | 이슈, 티켓, 카드(UI 요소를 가리킬 때만 "카드") |
| **Lead** | 그 **프로젝트**의 관리자. 배정·완료확정 권한 | PM, 관리자, 매니저 |
| **Member** | 그 **프로젝트**의 참여자 | 팀원(문서 서술에서는 허용), 사용자 |
| **Admin** | **워크스페이스** 관리자. 초대·프로젝트 생성 권한 | 슈퍼유저 |
| **배정 보드** | 사람이 컬럼인 보드. 프로젝트 내부 전용 | 칸반, PM 보드 |
| **내 업무 보드** | 상태가 컬럼인 보드. 본인 업무만 | 팀원 보드, My Tasks |
| **미배정** | `assigneeId IS NULL` 인 상태 | 백로그, 대기 |
| **완료 확정** | Lead가 `in_review → done` 으로 넘기는 행위 | 승인, 검수 |

**상태 4개의 공식 표기**

| 값 | 한글 | 색 |
|---|---|---|
| `todo` | 예정 | 🔵 |
| `in_progress` | 진행중 | 🟡 |
| `in_review` | 리뷰중 | 🟣 |
| `done` | 완료 | 🟢 |

## 4. 권한 매트릭스 (구현 기준)

> **읽는 법:** `WS` = 워크스페이스 역할, `PJ` = 그 프로젝트에서의 역할.
> **워크스페이스 Admin/Owner는 모든 프로젝트에서 PJ Lead로 취급한다** (D-016d).

| 행동 | 필요 권한 |
|---|---|
| 워크스페이스 설정 변경 · 양도 | WS `Owner` |
| 멤버 초대 / 워크스페이스에서 제거 | WS `Admin` |
| 프로젝트 생성 | WS `Admin` |
| 프로젝트 설정 변경 / 삭제 | PJ `Lead` |
| 프로젝트에 멤버 추가 / 제거 / 역할 변경 | PJ `Lead` |
| Task 생성 | PJ `Member` |
| Task를 **남에게** 배정 / 배정 해제 | PJ `Lead` |
| **미배정 Task를 본인이 가져가기** | PJ `Member` (US-403) |
| 본인 Task 상태 변경 (`todo`↔`in_progress`→`in_review`) | PJ `Member` |
| **`in_review → done` (완료 확정)** | PJ `Lead` |
| **`done → ` 되돌리기** | PJ `Lead` |
| 남의 Task 내용 수정 | PJ `Lead` |
| Task 삭제 | PJ `Lead` (본인이 만들고 미배정인 것은 Member도 가능) |
| 댓글 작성 | PJ `Member` |
| 댓글 삭제 | 작성자 본인 또는 PJ `Lead` |
| 프로젝트 조회 | PJ `Member` 또는 WS `Admin` |

**권한 위반 시 동작 (전 화면 공통)**
- 권한 없는 액션은 **UI에 아예 노출하지 않는다.** (비활성 버튼도 두지 않는다 — 왜 안 되는지 설명해야 해서 복잡해진다)
- 그럼에도 API로 요청이 오면 `403` 을 반환하고 **RLS 레벨에서도 차단**한다. UI 숨김을 보안으로 신뢰하지 않는다.

## 5. Epic & User Story

### E1. 온보딩 · 계정 · 워크스페이스

---

**US-101 · 워크스페이스 만들고 시작하기** 🔴 P0

> 나는 창업자로서, 가입하자마자 우리 회사 워크스페이스를 만들고 바로 팀을 초대하고 싶다.

**AC**
1. 이메일 + 비밀번호 또는 Google 계정으로 가입할 수 있다.
2. 가입 직후 소속 워크스페이스가 없으면 **워크스페이스 생성 화면**으로 강제 이동한다.
3. 워크스페이스 이름만 입력하면 생성된다. (다른 필수 입력 없음)
4. 생성자는 자동으로 WS `Owner` 가 된다.
5. 워크스페이스 생성과 동시에 **`개인 업무` 프로젝트가 자동 생성**된다 (D-014, D-023). 생성자는 이 프로젝트의 Lead다.
6. 한 사용자는 **워크스페이스 1개**에만 속한다 (D-022). 워크스페이스 전환 UI를 만들지 않는다.

---

**US-102 · 팀원 초대** 🔴 P0

> 나는 Admin으로서, 팀원을 이메일로 초대해 워크스페이스에 합류시키고 싶다.

**AC**
1. WS `Admin` 은 이메일 주소를 입력해 초대를 보낼 수 있다. 여러 개를 한 번에 입력할 수 있다.
2. 초대 시 **WS 역할(`Member`/`Admin`)을 지정**한다. 기본값은 `Member`.
3. 초대 메일에는 워크스페이스 이름 · 초대한 사람 이름 · 수락 링크가 들어간다.
4. 초대 링크는 **7일 후 만료**된다. 만료된 링크로 접속하면 "초대가 만료되었습니다. 초대한 분에게 다시 요청하세요" 를 보여준다.
5. 초대받은 사람이 링크를 누르면 → (계정 없음) 가입 후 자동 합류 / (계정 있음) 로그인 후 자동 합류.
6. 이미 워크스페이스에 있는 이메일로 초대하면 "이미 참여 중인 멤버입니다" 를 알린다.
7. 대기 중인 초대는 Settings에서 **재발송 / 취소**할 수 있다.
8. **초대할 때 참여할 프로젝트를 함께 지정할 수 있다** (D-033). 수락 즉시 해당 프로젝트의 `Member` 로 합류한다.
   - 프로젝트를 지정하지 않고 초대할 수도 있으나, 그 초대는 목록에 **`⚠️ 프로젝트 미배치`** 로 표시된다.
   - 근거: 워크스페이스 합류와 프로젝트 배치가 두 단계로 나뉘면 **두 번째가 잊히고**, 초대받은 사람은 빈 대시보드를 보고 이탈한다 ([03-USER-FLOW.md](03-USER-FLOW.md) §2 F0-B).

> 💡 **이메일이 필요한 유일한 지점이다.** 로그인 전이라 푸시를 보낼 수 없기 때문 (D-019a).

---

**US-103 · 첫 진입 온보딩** 🟠 P1

> 나는 처음 들어온 사람으로서, 뭘 해야 할지 헤매고 싶지 않다.

**AC**
1. 소속 프로젝트가 0개인 사용자에게는 대시보드 대신 **안내 화면**을 보여준다.
   - WS `Admin` → "첫 프로젝트를 만들어보세요" + 생성 버튼
   - WS `Member` → "아직 참여 중인 프로젝트가 없어요. 관리자에게 프로젝트 참여를 요청하세요"
2. 모바일에서 처음 접속하면 **"홈 화면에 추가" 안내**를 1회 보여준다 (US-802).
3. 안내는 닫을 수 있고, 닫으면 다시 뜨지 않는다.

---

**US-104 · 프로필 관리** 🟠 P1

**AC**
1. 이름 · 아바타 이미지를 수정할 수 있다.
2. 이름은 필수, 아바타는 선택. 아바타가 없으면 **이름 첫 글자 이니셜 원형**을 자동 생성해 쓴다.
3. 이메일은 계정 식별자이므로 v1에서 변경 불가.

### E2. 프로젝트

---

**US-201 · 프로젝트 생성** 🔴 P0

**AC**
1. WS `Admin` 만 생성할 수 있다.
2. 필수 입력은 **이름 하나뿐**이다. 나머지(설명·고객사·시작일·종료일·우선순위)는 전부 선택.
3. 생성자는 자동으로 그 프로젝트의 `Lead` 가 된다 (D-016e).
4. 생성 직후 **프로젝트 개요 화면으로 이동**하고, "팀원 추가" 와 "첫 업무 만들기" 를 다음 행동으로 제시한다.

> 💡 필수 입력을 이름 하나로 줄인 이유: Foundation §1 *"승부처는 입력 비용을 얼마나 낮추느냐"*. 생성 폼이 길면 프로젝트를 안 만들고 `개인 업무`에 다 몰아넣는다.

---

**US-202 · 프로젝트 멤버 관리** 🔴 P0

**AC**
1. PJ `Lead` 는 워크스페이스 멤버 중에서 골라 프로젝트에 추가할 수 있다.
2. 추가할 때 PJ 역할(`Lead`/`Member`)을 지정한다. 기본값 `Member`.
3. PJ `Lead` 는 멤버의 PJ 역할을 나중에 변경할 수 있다.
4. **프로젝트에 `Lead` 가 0명이 되는 변경은 차단**한다. 마지막 Lead를 제거하거나 강등하려 하면 "프로젝트에는 최소 1명의 Lead가 필요합니다" 로 막는다.
5. **멤버를 프로젝트에서 제거하면, 그 사람이 담당하던 Task는 전부 `미배정`으로 돌아간다.** (US-204)

---

**US-203 · 프로젝트 개요** 🟠 P1

**AC**
1. 개요 화면은 다음을 보여준다: 이름 · 설명 · 기간 · 상태 · 멤버 아바타 목록 · **진행률**.
2. **진행률 = 완료 Task 수 / 전체 Task 수** 로 계산한다. 저장하지 않는다 (D-009).
3. Task가 0개면 진행률 대신 "아직 업무가 없어요 → 업무 만들기" 를 보여준다.
4. 상태별 Task 개수(예정/진행중/리뷰중/완료)를 한 줄로 보여준다.

---

**US-204 · 담당자 이탈 처리** 🔴 P0

> 나는 Lead로서, 누가 프로젝트를 떠났을 때 그 사람 업무가 조용히 사라지지 않기를 바란다.

**AC**
1. 멤버가 프로젝트에서 제거되면, 그 사람이 담당(`assigneeId`)하던 **미완료 Task는 `assigneeId = NULL`(미배정)로 변경**된다.
2. `status` 는 **바꾸지 않는다.** (진행중이던 일은 진행중인 채로 미배정 컬럼에 남는다 — 어디까지 됐는지가 정보다)
3. 이때 PJ `Lead` 전원에게 알림을 보낸다: *"{이름}님이 프로젝트를 나가면서 업무 N건이 미배정이 되었습니다"*
4. 완료(`done`)된 Task는 담당자를 그대로 유지한다. **기록이므로 바꾸지 않는다.**
5. 워크스페이스에서 제거되는 경우에도 소속된 모든 프로젝트에 대해 동일하게 처리한다.

> ⚠️ **이 스토리가 없으면 사람이 나갈 때마다 업무가 유령이 된다.** 보드에 안 보이는데 DB에는 남아 진행률만 갉아먹는다.

---

**US-205 · 프로젝트 보관 / 삭제** 🟠 P1

**AC**
1. PJ `Lead` 는 프로젝트를 **보관(archive)** 할 수 있다. 보관된 프로젝트는 목록·대시보드·최상위 Tasks에서 빠지고, 별도 "보관됨" 탭에서만 보인다.
2. 보관은 되돌릴 수 있다.
3. **삭제는 보관된 프로젝트에 대해서만 가능**하다. 삭제 시 프로젝트 이름을 직접 입력해 확인받는다.
4. 삭제하면 소속 Task·댓글·문서 링크가 함께 삭제된다. 이 사실을 확인 화면에 명시한다.
5. `개인 업무` 프로젝트는 보관·삭제할 수 없다.

> 💡 **바로 삭제를 막고 보관을 거치게 한 이유:** 실사용 데이터가 들어간 뒤의 삭제는 되돌릴 수 없다(Foundation §12). 한 단계 미끄럼 방지턱을 둔다.

### E3. Task 기본

---

**US-301 · Task 만들기** 🔴 P0

**AC**
1. PJ `Member` 이상이면 만들 수 있다.
2. **필수 입력은 제목 하나뿐**이다.
3. 생성 시 기본값:
   - `status = todo` (**항상**, 예외 없음 — D-018)
   - `assigneeId` = 프로젝트 컨텍스트에서 Lead가 만들면 `NULL`, **그 외에는 만든 사람 본인**
   - `priority = normal`
4. 다음은 생성 시점에 선택 입력할 수 있다: 설명 · 담당자(Lead만) · 우선순위 · **시작일 · 마감일**.
5. **Task는 반드시 Project에 속한다** (D-014). 프로젝트를 고르지 않고 만들 수 있는 경로에서는 `개인 업무` 프로젝트로 들어간다.
6. 보드에서 만들면 **그 자리에서 인라인으로 제목만 입력**하고 Enter로 생성된다. 모달을 띄우지 않는다.
7. **담당자를 지정해서 만드는 경우, 마감일이 비어 있으면 입력을 요구한다** (US-304).

> 💡 AC-6이 Foundation §2 *"입력 비용"* 원칙의 가장 구체적인 적용이다. 업무 하나 적는 데 모달을 열고 폼을 채우게 하면 아무도 안 적는다.

---

**US-304 · 시작일 · 마감일** 🔴 P0

> 나는 Lead로서, 업무를 넘길 때 **언제까지인지**를 반드시 같이 정하고 싶다.
> 나는 팀원으로서, 내 업무가 언제 시작이고 언제까지인지 보고 싶다.

**AC**
1. Task는 `startDate` 와 `dueDate` 를 갖는다. 둘 다 **날짜 단위**다 (시각 없음 — 소규모 팀에 시간 단위 마감은 과하다).
2. **`dueDate` 는 "배정된 Task"에 대해 필수다.**
   - `assigneeId IS NULL` (미배정) → 마감일 **선택**
   - `assigneeId IS NOT NULL` (배정됨) → 마감일 **필수**
3. **배정하는 순간 마감일이 비어 있으면 그 자리에서 입력을 요구한다.**
   - 배정 보드에서 카드를 드롭하면 **작은 팝오버**가 뜨고, `오늘` `내일` `이번주 금` `다음주 금` **퀵칩 + 직접 선택**을 제공한다.
   - 이미 마감일이 있으면 팝오버는 뜨지 않는다. 드래그 한 번으로 끝난다.
   - `나중에 정하기` 로 건너뛸 수 있다. 건너뛴 Task는 **`⚠️ 마감일 없음`** 뱃지가 붙는다.
4. **`startDate` 는 항상 선택이다.** 비어 있으면 `in_progress` 로 처음 전환된 날짜가 자동으로 기록된다.
   - 즉 `startDate` 는 *계획된 시작일*이자, 없으면 *실제 시작일*이 된다. 나중에 수동으로 덮어쓸 수 있다.
5. **`startDate > dueDate` 인 조합은 저장할 수 없다.** 입력 시점에 막는다.
6. 마감일이 지난 미완료 Task는 카드에 🔴 로 표시된다 (US-402 AC-4).
7. 마감일은 담당자 본인과 PJ `Lead` 가 수정할 수 있다. **모든 마감일 변경은 활동 로그에 남는다** (US-603).
8. 마감일 없는 배정 Task 건수를 프로젝트 개요와 `전체 보기` 대시보드에 노출한다. (방치를 눈에 보이게)

> 💡 **왜 "생성 시 필수"가 아니라 "배정 시 필수"인가**
> 무조건 필수로 하면 백로그성 아이디어에도 아무 날짜나 찍게 된다. **아무렇게나 채운 필드는 빈 필드보다 나쁘다** — 지연 위젯이 거짓 경보를 내기 시작한다.
> 반대로 **배정은 "이 일을 언제까지 해주세요"라는 지시**다. 기한 없는 지시는 지시가 아니다. 그래서 기한을 요구하기에 정확히 맞는 순간은 생성이 아니라 배정이다.
>
> ⚠️ 이 규칙은 Foundation §2 철학 3번 *"배정은 드래그 한 번으로 끝난다"* 와 **일부 충돌**한다.
> 그래서 AC-3에서 ① 마감일이 이미 있으면 팝오버를 띄우지 않고 ② 퀵칩으로 한 번의 탭이면 끝나게 하고 ③ 건너뛸 수 있게 했다. **클릭이 한 번 늘어나되, 그 클릭이 없으면 지연 감지·캘린더·이번주 마감 위젯이 전부 동작하지 않는다.** 이 교환은 남는 장사다.

---

**US-302 · Task 수정 / 삭제** 🔴 P0

**AC**
1. 담당자 본인 또는 PJ `Lead` 는 제목·설명·우선순위·마감일을 수정할 수 있다.
2. `assigneeId` 변경은 PJ `Lead` 만 가능하다 (단, US-403의 "가져가기" 예외).
3. 삭제는 PJ `Lead` 가 할 수 있다. **본인이 만들었고 아직 미배정인 Task는 만든 사람도 삭제**할 수 있다.
4. 삭제 시 확인을 받고, 삭제 후 **10초간 되돌리기(Undo)** 를 제공한다.
5. 모든 수정은 `Activity` 에 기록된다 (US-603).

---

**US-303 · Task를 다른 프로젝트로 옮기기** 🟡 P2

**AC**
1. PJ `Lead` 는 Task의 소속 프로젝트를 변경할 수 있다. (양쪽 프로젝트 모두에서 Lead여야 한다)
2. **옮긴 뒤 담당자가 대상 프로젝트의 멤버가 아니면 `assigneeId = NULL` 로 초기화**하고 그 사실을 알린다.
3. 댓글과 활동 로그는 함께 이동한다.

### E4. 배정 보드 (Lead의 화면)

---

**US-401 · 드래그로 배정하기** 🔴 P0 ⭐

> 나는 Lead로서, 미배정 업무를 담당자에게 **한 번의 드래그로** 배정하고 싶다.

**이 스토리가 제품의 심장이다. 여기가 안 되면 나머지는 의미가 없다.**

**AC**
1. 프로젝트 > Tasks 탭의 기본 화면은 배정 보드다 (PJ `Lead` 기준).
2. 컬럼 구성 = `미배정` + **그 프로젝트 멤버 각각** (프로젝트 멤버만, 워크스페이스 전체 아님).
3. 컬럼 순서: `미배정` 이 항상 맨 왼쪽. 나머지는 이름 가나다순 (v1 기준, 사용자 정렬은 v1.1).
4. 카드를 다른 컬럼으로 드롭하면 **`assigneeId` 만 변경**된다. `status` 는 건드리지 않는다 (D-018a).
5. 드래그 결과는 **낙관적 업데이트**로 즉시 반영하고, 서버 실패 시 원위치로 되돌리며 토스트로 알린다.
5-1. **드롭한 Task에 마감일이 없으면 마감일 팝오버가 뜬다** (US-304 AC-3). 마감일이 이미 있으면 뜨지 않는다.
6. 배정되면 대상자에게 알림이 간다 (US-801).
7. **드래그는 PJ `Lead` 에게만 활성화**된다. Member에게는 같은 보드가 읽기 전용으로 보인다.
8. 각 컬럼 헤더에 **담당 중인 미완료 Task 개수**를 표시한다. (누가 과부하인지 즉시 보이게)

---

**US-402 · 카드에서 상태와 정체를 읽기** 🔴 P0

**AC**
1. 모든 카드는 **상태 뱃지**를 표시한다: 🔵예정 / 🟡진행중 / 🟣리뷰중 / 🟢완료
2. `in_progress` 또는 `in_review` 인 카드는 **현재 상태 경과일**을 함께 표시한다: `🟡 진행중 · 3일`
   - 경과일 = `now - statusChangedAt` (일 단위 내림)
   - 당일이면 "오늘"
3. 임계값을 넘으면 **🔴 지연** 뱃지를 추가한다.
   - 기본 임계값: `in_progress` **5일** 초과, `in_review` **2일** 초과
   - 임계값은 프로젝트 설정에서 변경할 수 있다.
4. 마감일이 지난 카드도 🔴 로 표시한다. (정체와 마감초과는 다른 사유이므로 툴팁으로 구분한다)
5. **마감일이 임박한 카드**는 `~D-1`, `오늘`, `D+3` 형태로 남은 일수를 표시한다.
6. **배정되었는데 마감일이 없는 카드**는 `⚠️ 마감일 없음` 뱃지를 붙인다 (US-304 AC-3).
7. 카드에 표시하는 것은 여기까지다. **제목 · 상태 뱃지 · 경과일 · 마감일 · 우선순위**. 더 넣지 않는다.

---

**US-403 · 미배정 업무 가져가기 (claim)** 🔴 P0

> 나는 팀원으로서, 미배정 업무 중에 내가 할 수 있는 걸 직접 집어가고 싶다.

**AC**
1. PJ `Member` 는 **`미배정` 컬럼의 Task에 한해** 본인에게 배정할 수 있다 ("내가 할게요" 버튼 또는 본인 컬럼으로 드래그).
2. **남에게 이미 배정된 Task를 가져올 수는 없다.** (뺏기 방지)
3. 본인이 가져간 경우에도 PJ `Lead` 에게 알림이 간다: *"{이름}님이 '{제목}'을 가져갔습니다"*
4. 본인에게 배정된 Task를 스스로 미배정으로 되돌리는 것은 **불가**하다. (조용한 업무 포기 방지 — 반납이 필요하면 Lead에게 말하거나 댓글로 남긴다)

5. 가져가기로 배정된 경우에도 마감일이 없으면 마감일 입력을 요구한다 (US-304 AC-3). 이때는 **본인이 스스로 기한을 약속하는 것**이므로 건너뛰기를 제공하지 않는다.

> 💡 Foundation §2 철학 4번 *"팀원도 자기 업무를 스스로 만들 수 있다"* 의 확장이다. 다만 AC-2, AC-4로 **가져가기는 되고 내려놓기는 안 되는** 비대칭을 뒀다. 업무가 조용히 주인을 잃는 상황을 막는 게 더 중요하다.
>
> **M1에 포함한다 (D-024).** 나중에 얹으면 배정 권한 판정과 알림 규칙을 다시 건드리게 되고, RLS 정책도 다시 써야 한다. **"본인에게만, 미배정 Task에 한해 assigneeId 설정 허용"** 은 배정 모델의 일부이지 부가 기능이 아니다.

---

**US-404 · 필터 칩** 🔴 P0

**AC**
1. 보드 상단에 필터 칩을 고정한다: `전체` `진행중` `리뷰 대기` `지연`
2. 칩 하나를 누르면 즉시 해당 카드만 남는다. **화면 이동 없이** 같은 자리에서 필터링된다.
3. `리뷰 대기` = `status = in_review` / `지연` = 정체 임계 초과 또는 마감 초과
4. 각 칩에 해당 건수를 표시한다. 0건인 칩은 흐리게 처리하되 숨기지는 않는다.
5. 필터 상태는 URL 쿼리에 반영해 **새로고침·공유 시 유지**된다.

---

**US-405 · 완료 카드 정리** 🟠 P1

**AC**
1. `done` 카드는 기본적으로 보드에서 **접혀 있다.** 각 컬럼 하단에 "완료 N건 보기" 로 접근한다.
2. 완료 후 **7일이 지난 카드**는 펼쳐도 기본 목록에 나오지 않는다. (프로젝트 > 완료 목록에서 조회)

### E5. 내 업무 보드 (모두의 화면)

---

**US-501 · 내 업무를 상태로 보기** 🔴 P0

**AC**
1. 최상위 `Tasks` 메뉴의 기본 화면은 **내 업무 보드**다. 역할과 무관하게 전원 동일하다.
2. 컬럼 = `예정` `진행중` `리뷰중` `완료`. 표시 대상 = **`assigneeId = 나`인 Task 전부** (프로젝트 횡단).
3. 각 카드에 **소속 프로젝트 이름**을 표시한다. (여러 프로젝트가 섞이므로 필수)
4. 드래그로 상태를 변경한다. `statusChangedAt` 이 갱신된다.
5. **`완료` 컬럼으로는 드롭할 수 없다.** 드래그를 시도하면 드롭 영역이 비활성으로 표시되고, 놓으면 *"완료 확정은 Lead가 합니다. 리뷰중으로 올려주세요"* 안내를 띄운다.
   - 단, 그 Task가 속한 프로젝트에서 내가 `Lead` 면 드롭할 수 있다.
6. 프로젝트별 필터를 제공한다.

---

**US-502 · 리뷰 요청** 🔴 P0

**AC**
1. Task를 `in_review` 로 옮기는 것이 곧 리뷰 요청이다. 별도 버튼을 만들지 않는다.
2. 그 프로젝트의 `Lead` **전원**에게 알림이 간다 (D-017).
3. 리뷰 요청 시 코멘트를 함께 남길 수 있다 (선택). 남기면 Task 댓글로 저장된다.

---

**US-503 · 완료 확정 / 반려** 🔴 P0

**AC**
1. PJ `Lead` 는 `in_review` Task를 **완료 확정**(`done`) 하거나 **반려**(`in_progress` 로 되돌림) 할 수 있다.
2. 완료 확정 시 `completedAt` 이 기록된다.
3. **반려할 때는 사유 입력이 필수**다. 사유는 Task 댓글로 저장되고 담당자에게 알림이 간다.
4. 담당자에게 결과 알림이 간다.
5. **Lead가 자기 자신의 Task를 완료 확정하는 것은 허용**한다. 소규모 팀에서 셀프 승인을 막으면 Lead의 업무가 영원히 리뷰중에 갇힌다. 다만 활동 로그에는 그대로 남는다.

> ⚠️ AC-3(반려 사유 필수)은 Foundation §1의 *"논의가 카톡으로 새어나가는 것"* 을 막는 장치다. 사유 없이 되돌리면 "왜 반려됐지?" 를 물으러 카톡으로 간다.

---

**US-504 · 최상위 Tasks 리스트 뷰** 🟠 P1

**AC**
1. 내 업무 보드에서 **리스트 뷰**로 전환할 수 있다.
2. 리스트 뷰에서는 **담당자 필터를 열어 다른 사람 업무도 볼 수 있다.** 단 내가 속한 프로젝트 범위 안에서만.
3. 필터: 프로젝트 · 담당자 · 상태 · 마감일 범위. 정렬: 마감일 · 우선순위 · 최근 변경.
4. **최상위 Tasks에서는 사람 컬럼 보드를 제공하지 않는다** (D-006a). 담당자별로 보고 싶으면 해당 프로젝트의 배정 보드로 이동한다.

---

**US-505 · 모바일에서의 내 업무** 🔴 P0

> 나는 팀원으로서, 출근길에 폰으로 "오늘 뭐 하지"를 확인하고 상태를 바꾸고 싶다.

**AC**
1. **모바일에서는 칸반 보드를 쓰지 않는다.** 상태 **탭 + 세로 리스트**로 표시한다.
   ```
   [ 예정 3 ][ 진행중 2 ][ 리뷰중 1 ][ 완료 ]
   ─────────────────────────────────────
   □ 로그인 API 연동        마케팅몬스터
     🟡 진행중 · 3일         ~7/28
   □ 소셜 로그인            마케팅몬스터
   ```
2. 상태 변경은 **드래그가 아니라 카드의 액션 버튼**으로 한다: `시작하기` → `리뷰 요청` (현재 상태에 따라 하나만 노출).
3. 배정 보드는 모바일에서 **읽기 전용**이다. 드래그 배정은 데스크톱 전용으로 명시한다.
4. 모바일에서도 Task 상세 · 댓글 작성이 가능해야 한다.

> ⚠️ **가로 4컬럼 칸반은 폰에서 동작하지 않는다.** 컬럼당 폭이 80px로 눌리고, 터치 드래그는 스크롤과 충돌한다. "반응형으로 줄이면 된다"가 아니라 **다른 화면이어야 한다.** 배정 보드(사람 컬럼)는 더 심해서 모바일 지원을 아예 포기하는 게 정직하다 — 배정은 앉아서 하는 일이다.

### E6. Task 상세 · 댓글 · 활동 로그

---

**US-601 · Task 상세** 🔴 P0

**AC**
1. 카드를 클릭하면 상세가 열린다. **전체 페이지 이동이 아니라 사이드 패널/모달**로 열어 보드 맥락을 잃지 않는다.
2. 표시 항목: 제목 · 설명 · 프로젝트 · 담당자 · 상태 · 우선순위 · 시작일 · 마감일 · 만든 사람 · 생성일
3. 상세에서 직접 상태 변경, 담당자 변경(권한 있을 때), 필드 수정이 가능하다.
4. URL이 바뀌어 **딥링크로 공유 가능**해야 한다. (알림에서 바로 이 Task로 진입)
5. `estimatedHours` / `actualHours` **필드는 없다** (D-008).

---

**US-602 · 댓글** 🔴 P0

**AC**
1. PJ `Member` 이상은 Task에 댓글을 쓸 수 있다.
2. `@이름` 으로 프로젝트 멤버를 멘션할 수 있고, 멘션된 사람에게 알림이 간다.
3. 본인 댓글은 수정·삭제할 수 있다. PJ `Lead` 는 남의 댓글도 삭제할 수 있다.
4. 댓글은 시간순으로 쌓인다. 스레드/대댓글은 v1에 없다.
5. 마크다운은 지원하지 않는다. 줄바꿈과 링크 자동 인식까지만.

> 💡 AC-4, AC-5는 의도적 축소다. 댓글이 문서 편집기가 되면 D-012(에디터 안 만듦)를 우회하게 된다.

---

**US-603 · 활동 로그** 🟠 P1

**AC**
1. Task 상세 하단에 **댓글과 같은 타임라인**으로 활동 로그를 섞어 보여준다. (별도 탭으로 분리하지 않는다 — 맥락이 끊긴다)
2. 기록 대상: 생성 · 담당자 변경 · 상태 변경 · 마감일 변경 · 완료 확정 · 반려 · 삭제
3. 각 항목은 `누가 · 무엇을 · 언제` 를 남긴다. 예: *"김대표님이 담당자를 이백엔드님으로 변경 · 2시간 전"*
4. **워크스페이스 Admin이 Lead 권한으로 개입한 경우 그 사실을 명시**한다 (D-016d): *"김대표님이(관리자 권한) 완료 확정"*

### E7. 대시보드

---

**US-701 · 내 업무 보기 (기본 화면)** 🔴 P0

**AC**
1. 로그인 후 첫 화면은 대시보드이고, **기본 탭은 `내 업무`** 다. 역할과 무관하다.
2. 위젯: `오늘 할 일` · `내 진행중 업무` · `이번주 마감` · `내 프로젝트`
   - `오늘 할 일` = 마감일이 오늘 이전이거나 오늘인 미완료 Task + 진행중 Task
3. 모든 위젯의 항목은 클릭하면 해당 Task 상세로 이동한다.
4. **빈 상태에서 회색 박스를 두지 않는다.** 각 위젯은 다음 행동 버튼을 보여준다. 예: *"오늘 할 일이 없어요 → 내 업무 보기"*

---

**US-702 · 전체 보기** 🔴 P0

**AC**
1. `전체` 탭은 **내가 Lead인 프로젝트가 1개 이상일 때만** 노출된다. (WS Admin은 항상)
2. 집계 범위 = **내가 `Lead` 인 프로젝트들**. WS `Admin`/`Owner` 는 전 프로젝트.
3. 위젯:
   | 위젯 | 정의 |
   |---|---|
   | 리뷰 대기 | `status = in_review` 인 Task 목록 (오래된 순) |
   | 지연 업무 | 정체 임계 초과 또는 마감 초과 Task |
   | 팀원별 진행중 업무 수 | 멤버별 `in_progress` **개수** (시간 아님 — D-008) |
   | 진행중 프로젝트 | 프로젝트별 진행률 바 |
   | 이번주 마감 | 이번 주에 마감인 Task |
4. `리뷰 대기` 위젯의 항목에서 **그 자리에서 완료 확정**할 수 있다. (Lead가 가장 자주 하는 행동이므로 클릭 깊이를 0으로)
5. Lead인 프로젝트가 여러 개면 프로젝트 필터를 제공한다.

### E8. 알림 · PWA

---

**US-801 · 알림 받기** 🔴 P0

**AC**
1. 다음 이벤트에 대해 **인앱 + 푸시** 알림을 보낸다.

   | 트리거 | 수신자 |
   |---|---|
   | 나에게 Task가 배정됨 | 담당자 |
   | 내 Task에 댓글/멘션 | 담당자 / 멘션된 사람 |
   | 리뷰 요청 (`→ in_review`) | 그 프로젝트 Lead 전원 |
   | 완료 확정 / 반려 | 담당자 |
   | 담당자 이탈로 업무가 미배정됨 | 그 프로젝트 Lead 전원 |
   | 마감 1일 전 / 마감 초과 | 담당자 |

2. **본인이 일으킨 이벤트는 본인에게 알리지 않는다.** (자기가 자기 Task 상태를 바꾸고 알림 받는 일 없음)
3. 인앱 알림은 헤더 벨 아이콘에 미읽음 뱃지로 표시된다. 클릭하면 해당 Task로 이동하고 읽음 처리된다.
4. **이메일 알림은 보내지 않는다** (D-019a). 초대 메일만 예외.
5. 알림 클릭 시 **해당 Task 상세로 딥링크**된다 (US-601 AC-4).

---

**US-802 · PWA 설치와 푸시 켜기** 🔴 P0

**AC**
1. `manifest.json` + 아이콘 세트를 제공해 홈 화면에 설치 가능하다. 설치 시 전체화면(standalone)으로 열린다.
2. **알림 권한을 자동으로 요청하지 않는다.** Settings와 온보딩에 **"알림 켜기" 버튼**을 두고, 사용자가 누를 때만 요청한다.
3. **iOS 안내**: iOS Safari로 접속했고 아직 설치되지 않았다면, "홈 화면에 추가해야 알림을 받을 수 있어요" 안내와 방법을 보여준다.
4. 권한을 거부한 사용자는 **인앱 알림만** 받는다. 제품은 정상 동작해야 한다.
5. Settings에서 현재 알림 상태(허용/거부/미설정)를 보여주고 다시 켤 수 있는 경로를 제공한다.
6. **데이터는 캐시하지 않는다** (D-019b). Service Worker는 앱 셸(JS/CSS/아이콘)만 캐시한다.
7. 오프라인 상태에서 접속하면 오래된 데이터를 보여주는 대신 **"연결이 필요해요" 화면**을 보여준다.

> ⚠️ AC-7이 D-019b의 실제 구현이다. 업무 도구에서 **틀린 데이터는 없는 데이터보다 나쁘다.**

**AC**

## 6. 상태 전이 규칙 (State Machine)

이 표를 벗어나는 전이는 **API와 RLS 양쪽에서 거부**한다.

| From | To | 누가 | 부수 효과 |
|---|---|---|---|
| `todo` | `in_progress` | 담당자 본인 · PJ Lead | `statusChangedAt` 갱신 |
| `in_progress` | `todo` | 담당자 본인 · PJ Lead | 〃 |
| `in_progress` | `in_review` | 담당자 본인 · PJ Lead | 〃 + PJ Lead 전원에게 알림 |
| `in_review` | `done` | **PJ Lead만** | 〃 + `completedAt` 기록 + 담당자 알림 |
| `in_review` | `in_progress` | **PJ Lead만** (반려) | 〃 + **사유 댓글 필수** + 담당자 알림 |
| `done` | `in_progress` | **PJ Lead만** (되돌리기) | 〃 + `completedAt` 초기화 |
| `todo` | `in_review` | ❌ 금지 | 시작하지 않은 일을 리뷰할 수 없다 |
| `todo` \| `in_progress` | `done` | ❌ 금지 | **리뷰 단계를 건너뛸 수 없다** |

> **`in_review` 를 건너뛰고 `done` 으로 갈 수 없게 한 것이 이 상태 기계의 핵심이다.**
> 이 규칙이 없으면 Lead가 "완료 확정"이라는 행동을 할 일이 없어지고, D-007 전체가 장식이 된다.
> **단, 담당자가 없는(`assigneeId IS NULL`) Task는 PJ Lead가 `todo → done` 으로 바로 닫을 수 있다.** (취소된 업무 정리용)

**배정 전이 (상태와 독립)**

| From | To | 누가 |
|---|---|---|
| `NULL`(미배정) | 임의 멤버 | PJ Lead |
| `NULL`(미배정) | **본인** | PJ Member (US-403) |
| 멤버 A | 멤버 B | PJ Lead |
| 임의 멤버 | `NULL` | PJ Lead · 멤버 이탈 시 자동 (US-204) |

## 8. 엣지 케이스 결정 모음

여기서 정하지 않으면 개발 중에 즉흥적으로 정해지고, 그 즉흥이 곧 버그가 된다.

| # | 상황 | 결정 |
|---|---|---|
| EC-1 | 프로젝트에 Lead가 0명이 되려 함 | **차단.** 최소 1명 유지 (US-202 AC-4) |
| EC-2 | 담당자가 프로젝트를 떠남 | 미완료 Task → 미배정. status 유지. Lead에게 알림 (US-204) |
| EC-3 | 담당자가 워크스페이스를 떠남 | 모든 프로젝트에 EC-2 적용 |
| EC-4 | 완료된 Task의 담당자가 떠남 | **담당자 유지.** 기록이므로 변경하지 않음 |
| EC-5 | Lead가 자기 Task를 완료 확정 | **허용.** 막으면 Lead 업무가 영영 리뷰중에 갇힘 (US-503 AC-5) |
| EC-6 | 팀원이 본인 업무를 미배정으로 반납 | **불가.** 조용한 업무 포기 방지 (US-403 AC-4) |
| EC-7 | 남에게 배정된 업무를 다른 팀원이 가져감 | **불가.** 미배정 Task만 가져갈 수 있음 |
| EC-8 | 미배정 Task를 닫아야 함 (취소된 업무) | PJ Lead는 `todo → done` 직접 가능 (§6) |
| EC-9 | 프로젝트를 옮겼는데 담당자가 그 프로젝트 멤버가 아님 | 담당자 초기화 + 알림 (US-303 AC-2) |
| EC-10 | 초대 링크가 만료됨 | 만료 안내 + 재요청 유도 (US-102 AC-4) |
| EC-11 | 알림 권한을 거부함 | 인앱 알림만. 제품은 정상 동작 (US-802 AC-4) |
| EC-12 | 오프라인 상태로 접속 | **캐시된 데이터를 보여주지 않고** "연결 필요" 화면 (US-802 AC-7) |
| EC-13 | `개인 업무` 프로젝트를 삭제하려 함 | **차단** (US-205 AC-5) |
| EC-14 | 마지막 Owner를 제거하려 함 | **차단** (US-1001 AC-3) |
| EC-15 | 두 사람이 같은 Task를 동시에 옮김 | 마지막 쓰기 승리. 활동 로그에 둘 다 기록되어 추적 가능 |
| EC-16 | 마감일 없이 배정하려 함 | 드롭 시 마감일 팝오버. `나중에 정하기` 가능하되 `⚠️ 마감일 없음` 뱃지 (US-304) |
| EC-17 | `startDate > dueDate` 입력 | **저장 차단.** 입력 시점에 검증 |
| EC-18 | 마감일 없는 Task가 `in_progress` 로 감 | 허용. 단 정체 감지(`statusChangedAt`)는 마감일과 무관하게 동작 |
| EC-19 | 배정 해제된 Task의 마감일 | **유지한다.** 다시 배정할 때 이미 채워져 있어 팝오버가 뜨지 않는다 |
| EC-20 | 마감일이 과거인데 완료됨 | 정상 저장. 지연 완료로 기록되며 뱃지는 사라진다 |

## 10. 마일스톤별 스토리 매핑

Foundation §12의 마일스톤에 스토리를 배치한 것이다.

| | 포함 스토리 | 완료 조건 | 상태 (2026-07-28) |
|---|---|---|---|
| **M1** 뼈대 | US-101, 102, 201, 202, 301, 302, **304**, 401, 402, **403** | 로그인 → 프로젝트 → Task → **드래그 배정 + 가져가기 + 마감일 지정이 끝까지 동작** | ✅ |
| **M2** 루프 완성 | US-501, 502, 503, 801, 802, 505 | 상태 변경 → 완료 확정 → **알림이 폰에 온다** ← 여기서 도그푸딩 시작 (D-020a) | ✅ |
| **M3** 실사용 진입 | US-601, 602, 603, 701, 702, 901, 404 | 대시보드 · 댓글 · 문서링크. **실제 프로젝트 1개 투입** | ✅ 기능 완료 |
| **M4** 전환 | US-103, 104, 204, 205, 405, 504, 1001 | 팀 전체 투입. 백업 확인 완료 | ✅ 기능 완료 · 백업 확인은 남음 |

> **M4 잔여분(US-103 · 405 · 504)과 US-203 을 함께 마감했다 (2026-07-28).**
> US-203(프로젝트 개요)은 M1 에 배치돼 있었으나 §3 을 "생성 후 보드로 이동" 으로
> 우회하면서 미뤄져 있었다 ([10-UX-AUDIT](10-UX-AUDIT.md) §7). 개요가 생겼으므로
> 생성 직후 목적지를 **US-201 AC-4 대로 개요로 되돌렸다.**
>
> **US-103 AC-1 은 코드가 있었지만 한 번도 실행되지 않았다.** 워크스페이스에 합류하면
> `개인 업무` 프로젝트가 자동 생성되므로(마이그레이션 17) 프로젝트 수가 0이 될 수
> 없었다. 이제 **개인 업무를 뺀 팀 프로젝트 수**로 판정한다.
>
> **모바일 `더보기`(`/more`) 가 Placeholder 로 남아 있었다.** IA §6 이 요구한
> 프로젝트 목록 · 설정 · 프로필을 채웠다. 하단 탭 4개 중 하나가 빈 화면이면
> 모바일 사용자는 사이드바에 있는 것들에 도달할 길이 없다.

> **M1 의 US-202(프로젝트 멤버 관리)는 M3 시점에 뒤늦게 발견해 채웠다** (`fad3e87`).
> 초대 수락만이 유일한 가입 경로여서 *이미 가입한 사람을 새 프로젝트에 넣을 수 없었다.*
> 혼자 쓰는 동안에는 드러나지 않는 종류의 구멍이었다.
>
> **도그푸딩 시작 시점은 M2 → 미정으로 미뤘다.** 제품 소유자가 팀 투입 전에
> 완성도를 더 올리기로 했다 (2026-07-28). 그 판단에서 나온 것이 [10-UX-AUDIT](10-UX-AUDIT.md) 다.

> **US-204(담당자 이탈 처리)를 M4에 둔 것은 위험을 감수한 배치다.** M3 도그푸딩 중에 사람이 프로젝트를 나가는 일이 생기면 그때 앞당긴다.

### §11-A. 정체 임계값이란 무엇인가

**한 줄 정의: "같은 상태에 며칠 이상 머물면 🔴 지연으로 표시할 것인가" 의 기준 숫자다.**

**예시로 보면**
```
월요일  김프론트가 '로그인 API'를 [진행중] 으로 옮김
화요일  🟡 진행중 · 1일
수요일  🟡 진행중 · 2일
목요일  🟡 진행중 · 3일
금요일  🟡 진행중 · 4일
다음주 월  🟡 진행중 · 5일  🔴 지연   ← 임계값이 5일이면 여기서 빨간불
```

**두 개를 따로 정하는 이유 — 원인이 다르다**

| 임계값 | 넘었다는 뜻 | 대응 |
|---|---|---|
| `in_progress` 임계 | **담당자가 막혔다.** 너무 큰 업무이거나, 다른 일에 밀렸거나, 뭔가 걸려 있다 | Lead가 물어본다 / 업무를 쪼갠다 |
| `in_review` 임계 | **Lead가 병목이다.** 팀원은 다 해놓고 확인을 기다리는 중 | Lead가 리뷰한다 |

`in_review` 임계가 훨씬 짧아야 하는 이유는, **리뷰 대기는 팀원이 아무것도 못 하고 멈춰 있는 시간**이기 때문이다.

**⚠️ 마감일 초과와는 다른 개념이다**

| | 기준 | 답하는 질문 |
|---|---|---|
| 마감 초과 | `dueDate` 가 지났나 | "약속한 날짜를 넘겼나?" |
| **정체** | `statusChangedAt` 이후 며칠인가 | **"진도가 안 나가고 있나?"** |

마감이 다음 달인 업무를 2주째 진행중으로 방치해도 **마감 초과는 안 잡힌다.** 정체 임계값이 그걸 잡는다.

**숫자를 잘못 잡으면 생기는 일**
- **너무 짧으면** → 정상 업무까지 전부 빨개진다 → 빨간불을 무시하게 된다 → **기능이 죽는다**
- **너무 길면** → 진짜 막힌 업무가 안 잡힌다 → **기능이 없는 것과 같다**

**✅ 확정 (2026-07-26) — D-027**

| | 값 | 근거 |
|---|---|---|
| `in_progress` 임계 | **5일** | 팀의 일반적인 업무 크기가 3~4일. 한 주를 넘기면 신호를 준다 |
| `in_review` 임계 | **2일** | 본업이 따로 있어 이틀 이내 확인이 현실적. 팀원 대기 시간의 상한 |

**5일을 고른 이유를 한 번 더:** 업무가 3~4일짜리인데 임계를 3일로 잡으면 **정상 업무가 매번 빨개진다.** 빨간불이 상시 켜져 있으면 아무도 안 본다. 실제 크기보다 **한 뼘 위**에 두어야 🔴가 신호로 기능한다.

- 두 값 모두 **프로젝트 설정에서 변경 가능**하다 (US-402 AC-3).
- 재검토 시점: **실사용 2주 후.** 판정 기준은 §11-C.
