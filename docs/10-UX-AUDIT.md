## 1. ✅ 해결 · 업무를 만든 뒤 어떤 필드도 수정할 수 없었다

> **반영 (2026-07-28)** — 업무 상세에 인라인 편집을 붙였다.
> 제목·설명은 눌러서 그 자리에서 고치고(blur 저장 · Escape 취소),
> 마감일은 기존 `DuePopover` 를 재사용하며, 우선순위·담당자는 select 다.
> 편집 모드를 따로 두지 않았다 — "수정" 버튼 → 폼 → "저장" 은 세 걸음이고,
> 오타 하나 고치는 데 세 걸음이면 안 고치게 된다.
>
> **완료된 업무는 편집을 막았다.** 완료 뒤 마감일을 고치면 완료 목록의
> "기한 내/지연" 판정이 사후에 바뀐다 — 기록이 말을 바꾸면 안 된다.
> 남에게 배정하는 것은 Lead 만 (서버 `tg_task_validate` 와 같은 기준).
>
> 구현: [use-update-task.ts](../apps/web/src/features/task/use-update-task.ts) ·
> [editable.tsx](../apps/web/src/features/task/editable.tsx)

### 증상 (당시)

업무 상세 패널이 보여주는 것: 제목 · 프로젝트 · 시작일 · 우선순위 · 기록.
이 중 **편집 가능한 것은 하나도 없다.** 상태 변경 버튼만 동작한다.

| 하고 싶은 일 | 지금 가능한가 |
|---|---|
| 제목 오타 고치기 | ❌ 지우고 다시 만들어야 한다 |
| 설명 추가·수정 | ❌ 입력란 자체가 없다 |
| 우선순위 변경 | ❌ |
| 담당자 변경 | △ 보드로 가서 드래그해야 한다 |
| 마감일 지정·변경 | ❌ **§1-A 참조 — 막다른 길이다** |

### 근거

- **US-601 AC-3**: *"상세에서 직접 상태 변경, 담당자 변경(권한 있을 때), 필드 수정이 가능하다"*
- **US-302**: Task 수정 / 삭제 — 삭제는 `bb4fb8c` 에서 구현했고 **수정은 미구현**

### 1-A. 마감일은 구조적으로 막혀 있다

가장 나쁜 형태의 결함이다 — **제품이 경고를 띄우면서 해결 수단을 주지 않는다.**

카드에는 `⚠️ 마감일 없음` 이 빨간 글씨로 뜬다 (US-402 · `is_missing_due`).
그런데 마감일 입력 팝오버는 [board-page.tsx:222](../apps/web/src/features/board/board-page.tsx#L222) 에서
**담당자가 바뀔 때만** 열린다:

```ts
if (assigneeId !== null && assigneeChanged && !task.due_date) { … }
```

내 컬럼에서 업무를 만들면 `assignee_id` 가 생성 시점부터 나다 →
담당자 변경이 영영 일어나지 않는다 → **마감일을 넣을 기회가 오지 않는다.**

유일한 우회로는 *미배정으로 드래그했다가 다시 나에게 끌어오는* 2단 드래그인데,
이걸 스스로 알아낼 사용자는 없다.

> 💡 D-021b(마감일은 배정 시점에 묻는다)는 **배정 흐름의 규칙**이지
> *마감일을 배정으로만 넣을 수 있다*는 뜻이 아니었다. 구현이 규칙을 좁게 읽었다.

### 제안

업무 상세에 인라인 편집을 붙인다. 별도 편집 모드를 만들지 않는다 —
값을 누르면 그 자리에서 바뀌고, 벗어나면 저장된다.

- 제목: 클릭 → textarea, blur 저장
- 설명: 비어 있을 때도 `설명 추가` 자리를 남긴다 (지금은 값이 없으면 영역이 사라진다)
- 마감일: 기존 `DuePopover` 재사용 — 이미 퀵칩(오늘·내일·이번주 금·다음주 금)이 있다
- 우선순위 · 담당자: select. 담당자는 Lead 권한일 때만 (US-601 AC-3)

서버는 이미 준비되어 있다 — `tasks_update` 정책, `tg_task_validate` 가 규칙을 판정한다.

**US-701 AC-2** 는 위젯 넷을 정의한다:

## 5. 사용자 제안 (2026-07-28)

실사용자(제품 소유자)가 직접 써보고 남긴 요구다. §1~3 이 *PRD 대비 누락*이라면
여기는 *PRD 에 없던 개선*이다. 근거가 수용 기준이 아니라 사용감이므로 구분해 둔다.

### 5-1. ✅ 생성은 인라인이 아니라 모달로

> **반영 (2026-07-28)** — 아래 **절충안을 택했다.**
> 업무·프로젝트 모두 모달이고, 업무 모달은 **누른 컬럼의 담당자가 이미 채워진 채로** 열린다.
> 제목 외에 마감일(퀵칩)·우선순위·설명을 함께 받으므로 §1-A 를 입구에서도 막는다.
> 프로젝트 모달은 이름만 필수이고 고객사·설명은 `고객사 · 설명 추가` 뒤로 접었다 —
> 폼이 길어 보이면 프로젝트를 안 만들고 `개인 업무` 에 몰아넣는다 (Foundation §1).
>
> **D-021b 는 폐기가 아니라 넓어졌다**: "배정할 때 마감일을 묻는다" 는 그대로 살아 있고,
> 생성·상세라는 두 입구가 추가됐다.
>
> 구현: [create-task-dialog.tsx](../apps/web/src/features/board/create-task-dialog.tsx)

**지금**: 업무 추가는 컬럼에 input 이 그대로 붙고([board-page.tsx](../apps/web/src/features/board/board-page.tsx)),
프로젝트 추가도 목록 위에 폼이 펼쳐진다([projects-page.tsx](../apps/web/src/features/projects/projects-page.tsx)).

**요구**: 항목을 만드는 행위는 모달로 띄운다.

> ⚠️ **D-021b · US-301 AC-6 과 충돌한다.** 인라인 생성은
> *"어느 컬럼에서 눌렀는지가 곧 담당자"* 라는 설계였고, 입력 비용을 낮추려는 의도였다
> (Foundation §1). 모달로 바꾸면 담당자를 폼에서 다시 골라야 한다.
>
> **절충안**: 모달을 띄우되 **누른 컬럼의 담당자를 미리 채운 상태로** 연다.
> 그러면 맥락은 유지하면서 제목 외 필드(마감일·우선순위·설명)도 생성 시점에 받을 수 있다 —
> §1-A 의 "마감일을 넣을 자리가 없다" 문제도 여기서 같이 해소된다.
> 이 절충을 택하면 D-021b 를 폐기하는 것이 아니라 **넓히는** 것이 된다.

### 5-2. ✅ 사이드바에 프로젝트 하위 트리

> **반영 (2026-07-28)** — `최근` 을 없애고 `프로젝트` 아래 트리로 대체했다.
> 잘라내지 않으므로 몇 개가 되든 1클릭이다 (D-030 충족).
> 펼침 상태는 `localStorage` 에 남고, 개인 업무는 맨 아래 고정이며(자물쇠 아이콘),
> 트리가 길어지면 트리 안에서만 스크롤한다 — 하단의 `설정` 을 밀어내지 않기 위해서다.

**지금**: 사이드바는 `대시보드 · 내 업무 · 프로젝트` 3개 + 별도의 `최근` 목록이고,
`최근` 은 [shell.tsx:54](../apps/web/src/app-shell/shell.tsx#L54) 에서 **상위 3개로 잘린다** (D-030).

**문제**: 프로젝트가 4개 이상이면 4번째부터는 `프로젝트` → 목록 → 클릭으로 **2클릭**이 든다.
`최근` 은 이름이 최근인데 실제로는 정렬 상위 3개일 뿐이라 기대와도 어긋난다.

**요구**: `프로젝트` 항목 아래에 하위 트리를 두고 접었다 펼 수 있게 한다.

- 펼침 상태는 기억한다 (localStorage). 매번 다시 펴게 하면 트리가 아니라 장애물이다
- 개인 업무는 트리 맨 아래 고정 — 개수가 늘어도 위치가 변하지 않아야 한다
- 프로젝트가 많아지면 트리 자체가 길어진다. 스크롤은 트리 안에서만 일어나게 한다
- D-030(배정 보드가 3클릭 깊이에 있으면 안 된다)의 **의도를 더 잘 지키는 변경**이다.
  `최근` 을 대체할지 병기할지는 구현 시 판단한다

### 5-3. ✅ 아이콘 색을 gray 톤으로

> **반영 (2026-07-28)** — 기본 `text-fg-muted`, hover·활성만 `text-fg`.
> fill 규칙(§D-052)은 그대로 유지했다.
> 규칙이 없던 자리라 **09-DESIGN-SYSTEM §3.3 에 절을 새로 만들어 적었다** —
> 다음에 아이콘을 놓는 사람이 같은 실수를 반복하지 않도록.

**지금**: 사이드바 아이콘이 `currentColor` 를 그대로 따라 본문색(거의 black)으로 렌더된다.
fill 스타일이 섞여 있어(D-052) 면적이 넓은 만큼 더 쨍하게 보인다.

**요구**: 아이콘만 gray 톤으로 낮춘다. **fill 규칙 자체는 유지한다.**

- 비활성 항목은 `text-fg-muted`, 활성 항목만 `text-fg` 로 올린다
- 09-DESIGN-SYSTEM 에 아이콘 색 규칙이 없다 — 이번에 정하고 그 문서에 적는다
- 뱃지·경고의 색(danger 등)은 대상이 아니다. 그건 상태를 말하는 색이다

**요구 (a)**: 10개씩 끊어 보여주고 더 불러오기 / 무한 스크롤.

**요구 (b)**: 무료 플랜 용량을 감안한 보존 정책을 미리 정해 둔다.

> 💡 **지금 당장의 위험은 낮다.** 무료 플랜은 500 MB 이고 현재 13 MB 다.
> 위 표를 산술로 늘려보면 알림·활동이 1만 행이 되어도 20 MB 안쪽이다.
> **먼저 할 일은 cron 추가가 아니라 목록 페이지네이션이다** —
> 지금 아픈 것은 용량이 아니라 화면이다.
>
> 다만 정책은 미리 정해 두는 편이 낫다. 검토할 축:
> - **미읽음 알림**: 지금은 영구 보존. 1년 넘은 미읽음은 사실상 죽은 알림이다
> - **activities**: 지우지 않는다는 원칙은 유지하되, 삭제된 Task 의 활동은
>   이미 FK cascade 로 함께 사라진다 — 별도 조치가 필요 없다는 사실을 기록해 둔다
> - 판정 기준: **DB 가 100 MB(무료 플랜의 20%)를 넘으면** 그때 보존 기간을 손본다.
>   그전까지는 숫자를 지켜보기만 한다
